## 1. 工作流发布与可执行工作流装配

### 链路范围

- **入口**：前端调用 `POST /api/v1/workflows/{workflowId}/publish`。
- **完成标志**：草稿版本被标记为可运行；之后第一次启动该版本时，每个 Agent 节点被装配为独立运行单元，并生成一份带版本摘要的执行计划。
- **包含的后续动作**：发布本身没有后台任务；Agent 装配发生在第一次启动这个发布版本时，装配结果保存在当前应用实例的内存缓存中。

### 文字链路

```text
用户在工作流画布点击发布
-> WorkflowController 从登录上下文取得租户、用户和角色，不接受请求体伪造身份
-> WorkflowDomainService 查询工作流和最新草稿，并检查当前用户是否有修改权限
-> 校验画布中的节点、边、入口节点、路由设置和基础运行参数
   - 没有草稿 -> 拒绝发布
   - 图结构不合法 -> 整个发布事务回滚，旧发布版本不受影响
-> 把这份草稿版本的状态从 DRAFT 改为 PUBLISHED，并记录发布人和发布时间
-> 把工作流主记录的 publishedVersion 指向刚发布的版本
-> 清除当前应用实例中这个工作流的旧装配缓存
-> 返回已发布的版本和画布内容

之后，用户第一次启动这个发布版本
-> loadRuntime 只允许读取状态为 PUBLISHED 的版本
   - 请求没有指定版本 -> 读取最新发布版本
   - 请求指定版本 -> 该版本也必须是已发布状态
-> 按“请求指定模型 > 节点模型 > 工作流默认模型”的顺序确定实际模型
-> 以 tenantId + workflowId + version + modelCode 组成当前实例的缓存键
   - 已有缓存 -> 直接复用已经装配好的执行计划和 Agent
   - 没有缓存 -> 进入首次装配
-> 编译器检查工作流类型和图结构
   - 普通工作流不允许出现环路
   - 智能工作流可以回到之前节点，但必须受总步数和单节点访问次数限制
-> 为每个 LLM 节点生成独立的内部 Agent ID、模型配置、指令和 Runner
-> 将画布边转换为只能从当前节点合法出口中选择的执行计划
-> 固定根节点、路由协议、总步数、Token 上限、每个节点允许到达的目标和单节点访问上限
-> 对整份执行计划计算 SHA-256 摘要，后续用于确认运行期间读取的仍是同一份定义
-> Armory 装配全部节点 Agent
   - 任一节点装配失败 -> 本次启动失败，不把半成品放入缓存
-> 全部装配成功后才写入当前应用实例的内存缓存
-> 返回“已经装配好 Agent 和节点配置、可以直接执行的工作流”
```

### 关键控制点

- **发布版本不会被草稿覆盖**：已发布版本和下一份草稿使用不同版本号。之后继续改草稿，不会改变已经启动的运行。
- **装配缓存范围**：缓存只在当前 Java 进程内，不是 Redis，也不会在多个实例之间共享。
- **模型覆盖会生成不同装配结果**：同一个工作流版本使用不同请求模型时，不会误用另一模型对应的 Runner。
- **环路边界**：智能工作流允许受控环路；编译计划会携带 `maxSteps` 和每个节点的 `maxVisits`。
- **全部成功才可使用**：所有节点装配成功后才写缓存，避免运行时拿到只装配了一部分的工作流。

### 当前实现审查

**已经达到的效果**

- 发布版本与草稿分离，后续修改草稿不会改变已发布版本的数据库内容。
- 第一次启动时按发布版本装配各节点 Agent，并生成包含合法路由范围的执行计划。
- 执行计划带定义摘要，后续工具调用和路由消费可以检查是否仍属于本次运行的版本。
- 智能工作流允许有限次数地回到旧节点，普通工作流仍要求没有环路。

**需要修正或明确的地方**

- 简历和讲解不能写成“发布时完成 Runtime 注册”。当前真实行为是“发布时固定可运行版本，第一次启动时才装配并注册 Agent”。
- 发布时的 `validateGraph` 与首次运行时编译器的智能图校验分处两个阶段。如果发布校验弱于编译校验，可能出现“发布成功、第一次运行才报错”。后续代码复查需要比较两套规则，并决定是否把所有确定性的图校验提前到发布阶段。
- 当前缓存只在单实例内。多实例部署时，每台实例都会各自装配一次，这不影响正确性，但不能描述成“全局只装配一次”。

### 源码证据

- `WorkflowController.publishWorkflow`
- `WorkflowDomainService.publishWorkflow / loadRuntime / compileRuntime`
- `WorkflowRuntimeCompiler.compileDag`
- `ArmoryService.acceptArmoryAgents`

## 2. 智能工作流启动与 Agent 执行

### 链路范围

- **入口**：前端调用 `POST /api/v1/intelligent-workflow-runs`，提交工作流、可选版本和模型、可选会话、用户问题、附件，以及可选的客户端运行编号。
- **完成标志**：成功时保存最终助手消息并把运行状态更新为 `COMPLETED`；失败或取消时分别保存为 `FAILED` 或 `CANCELLED`，同时产生可查询的终态事件。
- **包含的后续动作**：HTTP 事务提交后，由工作流协调线程继续执行节点；节点内部模型和工具调用完成后回到协调线程继续决定下一步。

### 文字链路

```text
前端提交智能工作流启动请求
-> Controller 从登录上下文取得可信租户、用户和角色
-> 将工作流、版本、模型、会话、问题、附件和 requestedRunId 交给运行服务
-> 运行服务加载指定的发布版本，并确认它确实是智能工作流
-> 如果请求没有 sessionId，则创建工作流会话
   - 会话记录保存实际生效的工作流版本和模型
   - 后续发布新版本不会让这次会话中途换配置
-> startOrResume 根据 requestedRunId 创建或查询 chat_run
   - 相同 requestedRunId 再次请求 -> 返回原运行，不重复创建
-> 查询智能工作流扩展状态
   - 已经存在 -> 直接返回原运行，不重复写用户消息，也不重复提交后台任务
-> 在同一事务中写入用户消息、绑定附件，并将消息绑定到本次运行
-> 创建智能工作流状态记录
   - currentNodeId = 根节点
   - status = RUNNING
   - executedSteps = 0
   - usedTokens = 0
   - 保存发布版本、定义摘要、总步数和 Token 上限
-> 保存 WORKFLOW_STARTED 事件
-> 数据库事务成功提交后，才把执行任务交给工作流协调线程池
-> HTTP 立即返回 runId、运行根 traceId、当前 HTTP 请求 traceId、状态和预算

后台协调线程开始执行
-> 使用运行根 traceId 继续记录后续日志
-> 把节点和边整理成按 nodeId 快速查找的表，从根节点开始
-> 每轮开始前重新读取运行状态
   - 已取消、已失败或已结束 -> 不再调用模型和工具
-> 检查当前节点存在，并增加该节点访问次数
   - 超过节点 maxVisits -> 运行失败，防止环路无限执行
-> 创建本次节点执行编号，先保存 RUNNING 节点审计和 NODE_STARTED 事件
-> 将用户问题、上一个节点输出、当前节点要求、合法路由和 RAG 使用说明合成提示词
-> 先登记本次模型调用；相同调用不能重复执行
-> 调用当前节点对应的 Agent
   - Agent 可以在这一轮中自主调用它被允许看到的 MCP、Skill、RAG 和路由工具
-> Agent 事件流完整结束后，将模型调用记录为成功
-> 保存节点输出事件，并从统一用量账本重新汇总本次运行实际消耗的 Token
-> 服务端决定下一节点并更新 currentNodeId
-> 下一轮根据新的 currentNodeId 取出对应 runtimeAgentId，再执行下一个 Agent
-> 直到进入 END
-> 再检查一次运行是否已被取消
-> 将最后一个节点输出作为最终回答，并结合累计 RAG 证据检查引用
-> 保存助手消息，将 chat_run 更新为 COMPLETED
-> 依次保存 FINAL_ANSWER_COMPLETED、WORKFLOW_COMPLETED 事件
-> 将智能工作流扩展状态更新为 END + COMPLETED

如果执行过程中出错
-> 模型调用和当前节点审计记录失败原因
-> 如果此时已经被用户取消
   -> 不走失败路线，不保存错误回答
   -> 结束仍在运行的节点记录，并发布 WORKFLOW_CANCELLED
-> 如果是普通技术异常
   -> 当前节点优先尝试走预先配置的 FAILURE 出口
   -> 没有可用失败出口或后续仍出错时，保存错误助手消息和 WORKFLOW_FAILED
   -> 将运行状态更新为 FAILED
```

### 关键控制点

- **启动请求重复提交**：`requestedRunId` 用来识别同一次启动。已经存在智能运行状态时直接返回，不重复写消息和执行节点。
- **事务提交后才执行**：只有运行记录、用户消息和首事件全部成功提交，后台任务才会启动，避免线程读到尚未提交的数据。
- **后台线程有明确容量**：协调线程池默认核心线程 1、最大线程 2、排队 8；队列满时会拒绝新任务。
- **循环有两层限制**：总执行步数受 `maxSteps` 限制，每个节点的访问次数受 `maxVisits` 限制；旧定义未填写单节点上限时使用 3，代码最终限制在 1 到 50。
- **Token 以账本为准**：路由前重新汇总会话用量，不直接相信模型返回的估算数字。
- **运行状态并发更新**：使用 revision 检查是否被其他请求抢先修改；短暂冲突最多重新读取并更新 3 次。

### 当前实现审查

**已经达到的效果**

- HTTP 请求与后台执行分离，浏览器断开不会中止工作流。
- 运行、用户消息、附件关系、智能工作流状态和首事件在事务中建立，提交后才开始执行。
- 每次节点执行都有独立编号、审计记录、事件和模型调用记录。
- 取消与失败分开处理，取消后不会错误地继续走 FAILURE 节点。
- 当前节点编号只有在服务端完成路由检查和数据库状态更新后才改变。

**修正后需要保留的边界**

- Agent 节点现在只对网络、超时、服务暂时不可用和限流等可能恢复的问题再次尝试，默认最多尝试 3 次；参数、权限等确定性错误不会重复调用。
- 协调线程池拒绝任务时会立即把运行改成失败并写入失败事件，不再长期停留在“执行中”。
- 当前运行只存在于某一实例的内存线程中，应用进程重启后没有看到从 `RUNNING` 状态继续执行的恢复链路。简历不能暗示具备进程重启恢复能力，除非后续补齐。

- `IntelligentWorkflowRuntimeService.start / execute / updateState`
- `RunControlService.startOrResume / appendUserMessage`
- `WorkflowExecutorConfig`
- `ChatService.invokeCompiledWorkflowNode / completeCompiledWorkflowRun`

## 3. Agent 提出路径、服务端确认路径并执行下一个 Agent

### 链路范围

- **入口**：非终点 Agent 在本轮执行中调用平台工具 `select_workflow_route(routeKey, reason)`。
- **完成标志**：服务端保存唯一的最终路径，更新运行的当前节点编号；下一轮按新节点找到对应 Agent 并执行。若没有任何合法出口，则运行以明确错误结束。
- **包含的后续动作**：路由工具调用发生在 Agent 的工具调用链中；Agent 返回后，工作流协调线程读取这次选择、完成最终检查并继续下一节点。

### 文字链路

```text
工作流编译器读取当前节点的所有出边
-> 只把当前节点允许选择的 routeKey、别名、edgeId 和目标节点放入可信运行上下文
-> Tool Resolver 动态生成 select_workflow_route 的参数范围
-> 当前 Agent 看到的是合法 routeKey 清单，看不到任意跳转能力

Agent 调用 select_workflow_route(routeKey, reason)
-> Tool Gateway 补入租户、用户、runId、工作流版本、定义摘要、节点执行编号和函数调用编号
-> 路由工具拒绝模型传入目标节点，只接受 routeKey 和 reason
-> 检查本次运行仍可执行，并确认这是智能工作流的新路由协议、当前节点不是终点
-> 在当前节点合法出口中精确匹配 routeKey 或受控别名
   - 不属于当前节点合法出口 -> 返回工具错误，不保存选择
-> 服务端提前解析出这条边真正对应的 edgeId 和 targetNodeId
-> 尝试保存“Agent 提出的下一步路径”，初始状态为 PENDING
   - 同一次函数调用再次到达且内容一致 -> 返回第一次的成功结果，不重复插入
   - 同一节点再次选择同一条边 -> 返回第一次的成功结果
   - 同一节点试图改选另一条边 -> 返回冲突，不覆盖第一次选择
-> 工具只告诉 Agent“选择已登记”，此时不修改 currentNodeId，也不调用下一个 Agent

当前 Agent 完成本轮输出并返回工作流协调线程
-> 运行服务按 tenantId + runId + nodeExecutionId 查询本轮保存的路径选择
-> 如果新协议节点没有调用路由工具，只发起一次补选请求
   - 补选时只允许调用 select_workflow_route，不重新做原节点任务
   - 补选成功 -> 重新查询选择记录
   - 补选仍未选择 -> 后面只允许走当前节点预先配置的 DEFAULT 出口
   - 补选发生技术异常 -> 尝试走 FAILURE 出口
-> 调用 IntelligentWorkflowRouter 做最终路径检查；这是一段确定性的 Java 规则，不是再次询问大模型
-> Router 先检查取消、总步数和 Token 上限
-> 再按固定顺序检查当前节点的出边
   - FAILURE -> FIXED -> SUCCESS -> EXPRESSION -> NODE_SUGGESTION -> AI_ROUTER -> DEFAULT
   - 同一策略有多条边 -> priority 较大的先检查；相同 priority 按 edgeId 固定排序
-> 命中边后，再确认目标节点属于当前节点允许到达的集合
-> 新协议下有 Agent 选择时，再比对工作流 ID、定义摘要和 edgeId
-> 在同一个数据库事务中完成四件事
   1. 把 Agent 的路径选择从 PENDING 改为 CONSUMED，保证只能使用一次
   2. 保存服务端确认的最终路径和原因
   3. 将当前节点审计更新为 COMPLETED
   4. 将智能工作流状态的 currentNodeId 更新为目标节点
-> 事务成功后才修改协调线程里的 currentNodeId
-> while 下一轮通过 nodes.get(currentNodeId) 找到目标节点
-> 读取目标节点的 runtimeAgentId
-> 调用该 Agent，形成“一个节点完成 -> 服务端确认路径 -> 下一个节点执行”的闭环
```

### 关键控制点

- **Agent 不能直接指定目标节点**：模型参数只有 `routeKey` 和 `reason`；真正的 `edgeId`、`targetNodeId` 来自服务端在当前节点合法出口中的匹配结果。
- **同一节点只能选择一次**：数据库唯一键限制 `(tenantId, runId, nodeExecutionId)`；同一个函数调用编号也只能对应一条记录。
- **最终决定必须执行**：即使 Agent 没有调用路由工具，服务端 Router 仍会运行，因为预算、失败出口、默认出口和目标范围都只能由它检查。
- **补选最多一次**：缺少选择时只让 Agent 补调一次路由工具，不会重新执行完整节点，也不会无限补选。
- **选择与节点推进一起提交**：路径选择的使用、最终路径记录、节点完成和当前节点更新处于同一事务，防止只完成其中一半。
- **路由顺序固定**：Router 不是自主推理模型；它只按已发布执行计划和固定优先级做可重复的判断。

### 当前实现审查

**已经达到的效果**

- “Agent 提出路径”和“服务端确认最终路径”已经明确分离。
- 路由工具本身不会推进节点；真正修改 `currentNodeId` 的代码位于运行服务。
- Agent 只能选择当前节点配置的合法路径，不能传入任意节点编号。
- 相同工具调用或相同节点的重复请求不会重复创建选择；试图改选另一条边会明确冲突。
- 缺少选择时最多补选一次，之后只能使用预先配置的默认出口；技术失败优先进入失败出口。

**简历表述需要保留的边界**

- 当前“自主路由”的准确含义是：Agent 在服务端提供的有限路径中自主选择，服务端再进行确定性检查；不是 Agent 可以自由决定任意下一个 Agent。
- 简历中的“读取 Runtime 注册表受控路由到对应 Agent”不够准确。代码实际读取的是本次发布版本编译出的节点表和边表，然后通过目标节点的 `runtimeAgentId` 找到已装配 Agent。建议改成“基于发布版本生成可执行节点表和合法出边，Agent 提交路径选择后由服务端校验并推进到对应 Agent”。
- “重试次数耗尽后固定到 END”仍不准确：服务端会先选择当前节点配置的失败出口；只有这个出口指向 `END` 时才直接失败结束。路由建议缺失只补选一次，之后通常走默认出口；预算耗尽以 `WORKFLOW_BUDGET_EXCEEDED` 失败，不会伪装成正常完成。
- `Router` 当前仍保留 `FIXED`、`SUCCESS`、表达式等旧策略。对新协议智能节点，是否应进一步限制策略组合，需要结合产品目标和现有工作流兼容性复查，不能仅凭简历文字删除。

## 4. Agent 每轮动态发现可用工具

### 链路范围

- **入口**：ADK 在每次向模型发起请求前调用 `GatewayToolset.getTools`，询问这一轮允许模型看到哪些函数。
- **完成标志**：这一轮可用的 Skill、MCP、RAG 和路由工具被转换成带名称、说明和参数规则的模型函数；不在清单里的能力无法被模型调用。
- **包含的后续动作**：没有消息队列或后台任务；工具清单只在当前模型调用中有效，下一轮会重新计算。

### 文字链路

```text
ChatService 准备执行某个 Agent 节点
-> 将租户、用户、会话、runId、上下文版本和 traceId 写入 ADK 的只读运行状态
-> 智能工作流额外写入当前节点编号、节点执行编号、发布版本摘要、MCP 白名单、RAG 开关和合法路由清单
-> ADK 在本轮请求模型前调用 GatewayToolset.getTools
-> GatewayToolset 只从服务端运行状态读取身份和工作流信息，不读取模型生成的文本
-> ToolResolver 按 tenantId + userId 查询数据库
-> 只保留当前用户有权使用、已发布并且存在激活版本的 Skill 和 MCP
   - 工具刚发布或停用 -> 下一轮查询立即反映，不需要重启或重新装配 Agent
   - 租户或用户缺失 -> 本轮直接失败，避免缺少隔离条件时误查工具
-> 如果是带节点配置的智能工作流，按当前节点 mcpIds 删除未配置的 MCP
-> PlatformToolResolver 根据运行条件临时生成平台工具
   - 会话采用 AGENT_TOOL、RAG 未关闭、节点允许且存在可信知识库范围 -> 加入 rag_retrieve
   - 智能工作流使用 TOOL_V2、当前不是终点且存在合法出边 -> 加入 select_workflow_route
-> 如果本轮只是让 Agent 补选路径，则删除除 select_workflow_route 之外的所有工具
-> 检查最终函数名是否重复
   - 两个工具规范化后同名 -> 拒绝本轮装配，避免模型调用落到错误工具
-> 为每个目录项创建 GatewayAdkTool
-> 固定这一轮模型看到的函数名、说明、参数类型、必填字段和工具版本
-> 把函数清单交给模型
-> 模型只能从这份清单中决定是否调用工具
-> 下一次模型请求重新执行整套解析，得到当时最新的能力清单
```

### 关键控制点

- **每轮重新读取**：普通 Skill/MCP 清单不做 Java 内存缓存，发布、停用和权限变化在下一轮生效。
- **身份由服务端提供**：模型参数不能提交 tenantId、userId 或 runId 来扩大权限。
- **平台工具按条件出现**：`rag_retrieve` 和 `select_workflow_route` 不是全局常驻工具，只在当前运行满足条件时生成。
- **路由参数动态收窄**：`select_workflow_route.routeKey` 的枚举值来自当前节点的合法出边。
- **补选能力最小化**：补选下一步路径时，模型只看得到路由工具，无法顺便再次调用 MCP、Skill 或 RAG。

### 当前实现审查

**已经达到的效果**

- 每次模型调用前都会重新生成工具清单，工具停用不需要重新启动应用。
- Skill、MCP 和平台工具最终都被包装成统一的 ADK 函数声明。
- RAG 与路由平台工具会根据会话、节点和发布版本中的可信配置动态出现。
- 智能工作流节点的 MCP 清单可以按节点 `mcpIds` 收窄。

**修正后需要保留的边界**

- `skillIds` 与 `mcpIds` 都已经进入节点执行计划；普通 DAG 和智能工作流都会把当前节点允许的工具清单带入运行上下文。
- 工具清单生成时先过滤一次，真正领取执行权前再核对一次，旧包装器也不能绕过节点范围。
- 每轮查库保证了停用及时生效，但工具目录较大时会增加数据库压力。是否引入带短过期时间和主动失效的缓存属于性能优化，不影响当前正确性审查。

## 5. 统一 Tool Gateway 调用

### 链路范围

- **入口**：模型选择本轮清单中的某个函数并提交业务参数，ADK 调用对应的 `GatewayAdkTool.runAsync`。
- **完成标志**：工具成功或失败结果被写入调用审计，并以统一结构返回模型；智能工作流节点还会产生可供前端继续读取的工具事件。
- **包含的后续动作**：Skill 会从 MinIO 读取已发布包；MCP 会连接远程 HTTP、SSE 或 stdio 服务；平台工具在应用内部完成 RAG 检索或登记下一步路径。

### 文字链路

```text
模型选择一个函数并提交参数
-> GatewayAdkTool 复制业务参数，避免修改 ADK 持有的原始对象
-> 从 ADK 运行状态重新构造租户、用户、会话、runId、节点执行编号、上下文版本、函数调用编号和 traceId
   - 身份字段不从模型参数读取
-> ADK 的 ToolExecutionGuardPlugin 在真实执行前读取数据库中的运行状态
   - 运行已取消、结束或被新运行替代 -> 返回阻断结果，工具不执行
   - 模型决策时使用的上下文已经被整理成新摘要 -> 阻止这次调用，让模型读取新上下文后重新判断
   - 状态有效 -> 放行到 ToolGateway
-> ToolGateway 再次检查工具标识和可信身份是否完整
-> ToolDispatchAuthorizationService 锁定运行记录，重新检查状态和上下文版本
-> 使用 tenantId + userId + runId + functionCallId + toolId 计算稳定调用键
-> 尝试插入状态为 STARTED 的工具调用审计
   - 首次插入成功 -> 获得唯一执行权
   - 唯一键已存在 -> 不再执行外部工具
      - 原记录成功 -> 返回第一次保存的结果
      - 原记录失败 -> 返回第一次保存的失败原因
      - 原记录仍是 STARTED -> 返回“结果暂时无法确认”，为避免重复外部操作不再执行
-> 保存 TOOL_CALL_STARTED 事件
-> ToolGateway 按类型分发
   - SKILL -> 从对象存储读取已发布 ZIP，在大小和条目限制内提取 SKILL.md
             -> 拼接 Skill 名称、版本、本次任务和说明正文
             -> 只把说明返回模型，不执行包内代码
   - MCP SSE/stdio -> 解析远程工具名和参数 -> 建立协议连接 -> 调用远程工具
   - MCP HTTP -> 将参数编码为 JSON -> 15 秒请求超时 -> 根据 HTTP 状态判断成功或失败
   - PLATFORM -> 根据函数名分发给 RAG 或路由处理器
-> 工具成功
   -> 将结构化结果、状态 SUCCESS 和总耗时写入调用审计
   -> 保存 TOOL_CALL_COMPLETED 事件
   -> 返回 {success: true, result: ...} 给模型继续推理
-> 工具失败
   -> 尽力把调用审计更新为 FAILED，并保存裁剪后的错误原因
   -> 保存 TOOL_CALL_FAILED 事件
   -> 返回 {success: false, error: ...} 给模型决定换参数、换工具或直接回答
```

### 关键控制点

- **两次运行状态检查**：ADK 插件先阻断明显无效调用，网关领取执行权时再在数据库事务和行锁下确认，降低取消与外部副作用并发发生的风险。
- **同一次函数调用只执行一次**：稳定调用键和数据库唯一索引共同决定执行权；重复请求只返回第一次结果。
- **结果不确定时不冒险重试**：审计仍停在 `STARTED` 时，系统无法证明外部操作未发生，因此不会自动再执行。
- **Skill 不执行代码**：Skill 调用的实际效果是读取 `SKILL.md` 并交给模型，不是运行用户上传的脚本。
- **MCP 不自动重试**：远程工具可能有下单、写入等副作用，网关不会在网络异常后自行重发。
- **智能节点事件可继续读取**：有 `workflowId + nodeExecutionId` 时，开始、成功和失败事件都进入统一工作流事件表。

### 当前实现审查

**已经达到的效果**

- Skill、MCP 和平台工具通过同一个 `ToolGateway` 完成运行门禁、唯一执行权领取、类型分发、结果审计和事件记录。
- 模型只能控制工具的业务参数，不能控制租户、用户、运行和工作流版本等身份字段。
- 同一函数调用重复到达时不会再次产生外部消耗。
- 工具错误被转换为模型可理解的结构，同时完整异常仅进入服务端日志。

**需要修正或明确的地方**

- 没有 `runId` 或 `functionCallId` 时，调用键会退化为随机值，此时只能留下审计，不能阻止重复执行。正式 Agent 运行应保证这两个字段始终存在，并增加测试证明；独立内部调用则必须明确接受这一风险。
- 工具执行成功但最终审计写入失败时，外部副作用已经发生，记录可能长期停在 `STARTED`。当前保守策略能阻止再次执行，但缺少自动核对外部结果并修正审计的流程。
- MCP HTTP 兼容路径不是标准 MCP 协议调用，只是普通 JSON POST；简历可写“统一支持 HTTP/SSE/stdio 工具分发”，但面试时要说明 HTTP 是兼容适配通道。
- `TOOL_CALL_FAILED` 的事件字段当前固定 `retryable=false`，而返回模型的行为允许模型重新生成新的函数调用。需要统一“是否值得重新尝试”的语义，避免前端和模型理解不一致。

### 未展开的外部边界

- **MinIO**：代码可确认读取的桶和对象键来自已发布 Skill 版本；对象存储内部可靠性不在本仓库实现。
- **远程 MCP 服务**：代码可确认请求协议、超时和响应处理；远端工具是否真正完成业务动作只能由对方响应或额外查询接口确认。
- **Google ADK / 模型服务**：代码可确认函数声明和工具结果的交付方式；模型为何选择某个工具属于外部模型行为。

- `ToolGateway.invoke / dispatch / invokeSkill / invokeMcp`
- `ToolDispatchAuthorizationService.claim / finish`

## 6. Agent 主动 RAG、多次检索、预算和证据

### 链路范围

- **入口**：采用 `AGENT_TOOL` 调用方式的运行中，模型调用平台工具 `rag_retrieve(query, maxContextTokens)`。
- **完成标志**：本次检索上下文和引用编号返回模型，实际注入的证据被绑定到本次模型调用；运行结束时，最终回答中的引用编号与证据清单完成比对并写入消息元数据。
- **包含的后续动作**：模型读取第一次检索结果后，可以修改问题再调用一次形成多次检索；没有消息队列，检索和证据登记都在工具调用线程内同步完成。

### 文字链路

```text
会话采用 AGENT_TOOL，RAG 未关闭，当前 Agent 节点允许使用 RAG
-> PlatformToolResolver 在本轮工具清单中加入 rag_retrieve
-> 模型根据用户问题和已有中间结果决定是否检索
-> 模型调用 rag_retrieve，只能提交 query 和可选 maxContextTokens
   - query 最长 2000 字符
   - maxContextTokens 范围 128 到 8000，未填写时使用 8000
   - 租户、用户、知识库范围和绑定编号不能由模型提交
-> Tool Gateway 完成运行状态检查、重复调用保护和工具审计
-> RagRetrievePlatformToolHandler 从可信运行上下文读取本次运行固定的知识库绑定范围
-> 在发起检索前预留一次调用次数和本次最大 Token 数
   - 默认每个 run 最多调用 3 次
   - 多次调用实际返回的上下文累计不超过 8000 Token
   - 本次预留会让总额度超限 -> 直接返回 RAG_TOOL_BUDGET_EXCEEDED，不调用检索服务
-> RagRetrievalService 在固定绑定范围内完成召回、融合、重排和上下文补全
-> PresentationService 将结果包装成明确标记为“不可信参考资料”的上下文
   - 文档正文中的命令和角色要求没有指令权限
   - XML 特殊字符被转义，避免文档正文改变上下文结构
   - 每条资料携带平台生成的 citationId
-> 检索返回后再次读取运行状态
   - 用户在检索期间取消运行 -> 不把迟到结果登记为可引用证据
-> 按 tenantId + userId + sessionId + runId + 本次模型调用编号登记证据
-> 按实际返回的 Token 数结算，归还本次预留但未使用的额度
-> 将 context、citations、命中数、Token、耗时和是否降级返回模型
-> 模型继续推理
   - 资料足够 -> 生成答案
   - 资料不足或发现新线索 -> 换一个更具体的问题再次调用 rag_retrieve
   - 达到 3 次或累计 Token 上限 -> 后续检索被拒绝，模型只能使用已有资料作答
-> 每次成功检索的证据按模型调用编号累积到本次运行
-> 节点结束时取回这次节点调用实际登记的证据
-> 工作流运行结束时汇总全部节点证据
-> 从最终回答中提取 cite_xxx 格式的引用编号，与证据清单逐项比对
   - 没有使用 RAG -> NO_RAG
   - 有资料但回答未引用 -> RAG_AVAILABLE_UNUSED
   - 所有引用都能在证据清单中找到 -> VALID
   - 出现证据清单外的引用 -> INVALID_CITATIONS
-> 将引用检查状态、检索批次和实际使用的出处写入最终助手消息元数据
-> 清除本次运行在当前进程中的临时证据
```

### 关键控制点

- **多次检索由 Agent 决定**：系统不会硬编码第二次查询；模型可以依据第一次结果改写问题，再发起新的函数调用。
- **运行范围固定**：工具使用运行创建时保存的绑定编号；绑定失效时明确失败，不会静默换成别的知识库。
- **先预留再结算**：并发调用先占住最大额度，完成后再按实际 Token 归还差额，避免同时检索造成超额。
- **失败不消耗额度**：参数错误或检索异常会退回本次调用次数和 Token 预留；正常返回空结果仍算一次有效检索。
- **资料按不可信输入处理**：检索正文只提供事实参考，不能覆盖系统、用户或工作流要求。
- **引用只认可真正注入过的证据**：模型自己编造一个形式正确的 citationId，也会被标记为非法。

### 当前实现审查

**已经达到的效果**

- RAG 已作为平台工具进入与 MCP、Skill 相同的统一工具调用链。
- 模型可以依据中间结果连续提交不同问题，形成最多 3 次的多次检索。
- 每次运行同时受调用次数和累计上下文 Token 限制。
- 知识库范围、运行身份和绑定快照来自服务端，模型不能在参数中切换目标知识库。
- 检索结果、证据登记、最终回答引用检查已经形成可追踪关系。

**简历表述需要保留的边界**

- **预算只存在当前 Java 进程内。** 多实例之间不共享，应用重启后也会清空；条目 1 小时未访问还会被删除。分布式部署下无法保证真正的单运行全局上限，目标设计应改为 Redis 或数据库中的原子计数，并在运行终态清理。
- **证据也只存在当前进程内。** 正常情况下节点执行和最终收尾在同一实例可用；进程重启或跨实例接管时会丢失。若目标包含运行恢复，需要把证据保存到可共享存储。
- **引用检查当前只记录结果，不阻止错误回答。** 即使状态为 `INVALID_CITATIONS`，原回答仍会保存为最终助手消息。简历可写“绑定并审计引用证据”，不能写成“阻止模型伪造引用”；若目标要求强保证，需要在落库前拒绝、移除未知引用或让模型修正一次。
- 检索配置中存在 `queryRewriteEnabled`，但当前没有问题改写器。开启后只记录 `query_rewrite_unavailable` 并继续使用原问题。现阶段“问题调整”来自 Agent 再次调用时主动改写，不是检索服务自动改写。

### 未展开的外部边界

- **Embedding 服务**：仓库能确认请求类型、向量用途和失败处理，模型内部如何生成向量属于外部服务。
- **Qdrant**：仓库能确认租户、知识库和索引代次过滤条件，Qdrant 内部近邻搜索实现属于外部系统。
- **Rerank 服务**：仓库能确认送入的候选和返回分数校验，模型自身排序逻辑属于外部服务。

## 7. Dense、Sparse、RRF、Rerank 与上下文补全

### 链路范围

- **入口**：`RagRetrievalService.retrieve` 收到已经带有可信租户、用户、运行绑定范围、检索问题和上下文 Token 上限的请求。
- **完成标志**：返回按相关性和 Token 上限裁剪后的引用列表；检索配置、各阶段候选数、耗时、降级原因和最终出处被写入检索审计。
- **包含的后续动作**：没有异步续接；Embedding、Qdrant 搜索和 Rerank 都在当前检索调用内完成。

### 文字链路

```text
RagRetrievalService 接收检索请求
-> 去除问题首尾空白并规范化可检索文本，生成 retrievalId
-> 查询当前 Agent 或工作流目标配置的知识库绑定
-> 使用运行开始时保存的 bindingIds 收窄范围
   - 固定绑定中有任何一项已经消失 -> 整次检索失败，不改用新绑定
   - 绑定总数超过 32 -> 拒绝检索
-> 对每个绑定读取知识库和检索配置
-> 检查知识库当前可搜索、已经有启用的索引版本，并检查私有知识库所有者
   - 必需绑定不可用 -> 整次检索失败
   - 可选绑定不可用 -> 跳过并继续其他绑定
-> 如果任一配置需要 Dense，调用 Embedding 服务把问题转换为查询向量
-> 如果任一配置需要 Sparse，使用固定词表版本将问题转换为稀疏词项权重
   - 某一路失败且必需绑定依赖它 -> 整次检索失败
   - 只有可选绑定依赖它 -> 移除这些绑定，保留仍可运行的检索通道并记录降级原因

对每个仍可用的知识库绑定执行
-> 只在 knowledgeBaseId + currentGeneration 范围内搜索，旧索引版本不能混入
-> 根据配置执行一种或两种召回
   - DENSE -> Qdrant 按语义向量取 denseTopK
   - SPARSE -> Qdrant 按关键词权重取 sparseTopK
   - HYBRID -> 两路都执行
-> 按 chunkId 合并两路命中，并确认同一 chunkId 的文档、版本和索引代次一致
-> 根据配置计算统一分数
   - 单路 -> 将原始分数转换到 0 到 1
   - RRF -> 根据两路排名按 1 / (60 + rank) 合并，再归一化到 0 到 1
   - WEIGHTED -> 两路分数分别归一化后按 denseWeight 和 sparseWeight 加权
-> 删除低于 scoreThreshold 的候选，按融合分排序并保留 fusionTopK
-> 按 chunkId 从 MySQL 读取完整业务分块
-> 逐项确认 Qdrant 命中与数据库分块属于同一租户、知识库、文档、版本和索引代次
-> 删除正在清理的旧记录和 contentHash 相同的重复内容
-> 如果启用 Rerank
   -> 取前 rerankTopK 个候选和原问题交给 Rerank 服务
   -> 拒绝 Rerank 返回未知或重复 chunkId
   -> 按 Rerank 分数重排并保留 finalTopK
   -> Rerank 调用失败 -> 记录降级原因，退回融合排序，不让整个检索失败
-> 如果未启用 Rerank，直接按融合排序保留 finalTopK

合并多个知识库绑定的结果
-> 按 chunkId 去重，同一分块只保留分数更好的结果
-> 按最终分数形成全局候选顺序
-> 对每个主命中读取它的父块
-> 再按 neighborWindow 沿 previousChunkId 和 nextChunkId 向两侧补充相邻块
-> 每个补充块都必须与主命中属于同一知识库、文档、版本和索引代次
-> 按 chunkIndex 恢复原文阅读顺序，将小块、父块和相邻块拼成引用上下文
-> 同时检查三层数量限制
   - 每个检索配置的 finalTopK
   - 每个绑定的 maxTokens 与检索配置 maxContextTokens 中较小者
   - 本次请求的全局 maxContextTokens
-> 超出上限的整条候选不加入上下文，不截成无法核对出处的半段文本
-> 为接纳的候选生成 citationId，保存文档、版本、页码、标题路径、主 chunkId 和内容摘要
-> 写入各阶段候选数、耗时、配置版本、降级原因和最终引用审计
-> 返回引用列表和实际上下文 Token 数
```

### 关键控制点

- **索引版本隔离**：检索只查询知识库当前启用的索引批次（代码字段为 `generation`），并回到 MySQL 逐项核对，防止 Qdrant 残留旧向量进入答案。
- **RRF 常数**：排名倒数融合使用 `k=60`，降低单路排名靠前候选对结果的过度支配。
- **候选数量分阶段控制**：`denseTopK / sparseTopK -> fusionTopK -> rerankTopK -> finalTopK`，每一层含义不同。
- **Rerank 可以降级**：Rerank 服务故障时使用融合顺序继续返回，并明确记录降级原因。
- **小块命中、大块补全**：搜索命中使用精确分块，返回模型前补上父块和设定窗口内的相邻块。
- **预算按完整引用计算**：扩展后的整段上下文才参与 Token 计算，避免搜索阶段看似很小、补全后挤爆上下文。

### 当前实现审查

**已经达到的效果**

- 支持 Dense、Sparse、Hybrid 三种模式，以及 RRF 和加权分数两种融合方式。
- 支持按配置启用 Rerank，失败时有明确降级路径。
- 向量命中会回到业务数据库检查租户、活动文档版本和索引代次，不直接信任 Qdrant 负载。
- 主命中可以扩展父块和多层相邻块，并按原文顺序组装上下文。
- 检索结果带完整引用定位与阶段审计，可用于后续调试和评测。

**需要修正或明确的地方**

- 配置支持 `queryRewriteEnabled`，但问题改写尚未真正执行；该能力不能作为当前检索流水线的已实现阶段。
- Sparse 使用项目内固定词表编码器，不是独立的学习型稀疏检索模型。简历可以写 Sparse 检索，但面试时不能暗示使用了 SPLADE 等未接入模型。
- 父块和相邻块都会加入同一引用的上下文，但引用定位仍以主命中的 `chunkId`、页码和标题为主。跨页父块或相邻块的精细出处展示需要进一步评估。
- 当前候选若扩展后超过剩余 Token，会整条跳过，未尝试缩小相邻窗口或只保留主块。这保证出处完整，但可能浪费剩余额度；是否分级收缩需要用评测数据决定。

## 8. Redis 保存近期对话并组装模型上下文

### 链路范围

- **入口**：用户消息或助手回答保存到 MySQL 后，记忆服务收到“消息已经保存”的通知；下一次调用模型时，聊天服务请求组装当前会话的上下文。
- **完成标志**：模型收到一份没有超过窗口预算的背景信息，其中包含可用的长期摘要、最近有效对话、上游节点输出、附件和按需检索结果；Redis 不可用时仍能从 MySQL 读取原始消息完成组装。
- **包含的后续动作**：消息保存后更新 Redis；模型调用前读取 Redis，缓存没有数据或读取失败时回到 MySQL，并用数据库结果重新填充缓存。

### 文字链路

```text
用户消息或助手回答先保存到 MySQL
-> 每条消息取得会话内递增的 sequenceNo，后续用它恢复原始对话顺序
-> 记忆服务把已经保存成功的消息追加到 Redis 最近消息列表
   - Key：ctx:recent:{tenantId}:{userId}:{sessionId}，不同租户、用户和会话互不混用
   - 排序分数：sequenceNo，保证按数据库消息顺序读取
   - 同一 sequenceNo 再次写入：先删除旧内容再写新内容，避免同一位置留下两份消息
   - 最多保留最近 100 条，开发配置下 30 分钟没有访问后自动过期
-> Redis 写入失败只记录日志；MySQL 中的原始消息仍然保留，不影响后续恢复

下一次准备调用模型
-> 先确认上下文管理已经开启，并根据模型窗口计算本轮可使用的总额度
-> 从模型最大窗口中先扣除回答预留 8192 Token 和计数误差余量 2048 Token
-> 查询当前有效的长期摘要
   - 先读 ctx:snapshot:{tenantId}:{userId}:{sessionId}
   - 缓存没有数据或读取失败 -> 从 MySQL 读取当前有效摘要，并重新写入 Redis
-> 从摘要已经覆盖到的消息序号之后开始读取近期对话
-> 只读取本次模型调用允许看到的最大消息序号之前、并且仍然有效的消息
   - 用户取消本轮或追加新要求后，被标记为失效的旧消息不会进入上下文
-> 先读 Redis 最近消息列表
   - Redis 中存在这个会话的列表 -> 直接按消息序号读取指定范围
   - Redis 中没有这个列表或读取失败 -> 从 MySQL 读取，并把结果重新放入 Redis
-> 从最新消息向前选择连续的完整消息
   - 最近对话单独最多使用 8192 Token
   - 超出额度时在消息边界停止，不把一条消息截成半段
   - 即使最新一条消息本身较长，也至少保留这条完整消息
-> 将长期摘要、最近对话、上游节点输出、附件和按需 RAG 结果分别包装成有明确边界的候选内容
-> 按“长期摘要 -> 最近对话 -> 上游输出 -> 附件 -> RAG”的优先级依次选择完整内容
-> 每一类先受自己的额度限制，所有内容还要共同遵守本轮总额度
-> 某段内容放入后会超过总额度 -> 整段不放入，不截断附件或引用证据
-> 生成最终背景信息，并记录各类内容实际使用的 Token、覆盖的消息范围和是否发生裁剪
-> 聊天服务把这份背景信息连同当前用户问题交给 Agent
```

### 关键控制点

- **MySQL 保存完整历史，Redis 只负责加快读取**：Redis 丢失、过期或暂时不可用不会造成会话历史永久丢失。
- **消息顺序稳定**：Redis ZSet 使用 `sequenceNo` 排序；同一序号先删后写，避免旧 JSON 和新 JSON 同时存在。
- **缓存有明确上限**：开发配置默认最多 100 条、有效 1800 秒，防止长期会话无限占用 Redis。
- **只使用当前仍有效的消息**：上下文查询受消息有效状态和本次调用可见序号限制，取消后的旧回答不会继续影响模型。
- **两级额度控制**：每类内容有独立上限，全部内容还共享模型窗口扣除回答额度和安全余量后的总上限。
- **尽量保留完整语义**：近期对话在消息边界停止，附件和 RAG 引用也按完整片段取舍。

### 当前实现审查

**已经达到的效果**

- Redis 能按会话和消息序号维护最近对话，失效后可以从 MySQL 重新建立。
- 长期摘要与近期消息分开保存，组装时只读取摘要尚未覆盖的消息。
- 上下文装配同时控制单类额度和模型总窗口，并能输出实际使用量和裁剪原因。
- 被取消或被新要求替代的消息不会继续送入模型。

**需要保留的边界**

- `ContextAssemblyResult.cacheHit` 会反映长期摘要是否直接从 Redis 命中；近期消息缓存只是加速读取，不是完整历史来源。
- Redis 最近消息最多保留 100 条。读取时必须连续覆盖所需序号；缺少开头、结尾或中间任何一条，就放弃这次缓存结果并从 MySQL 重新读取完整区间。
- 主配置中的上下文管理默认关闭，开发配置才默认开启。准确表述应是“启用 Context Manager 后使用 Redis 短期记忆”，不能说所有部署环境天然启用。

## 9. 将较早对话整理成长期摘要

### 链路范围

- **入口**：助手回答保存后，记忆服务检查尚未进入长期摘要的消息量；或者模型已经决定调用工具、真正执行工具前，再检查一次当前上下文是否已经过长。
- **完成标志**：较早的有效对话被整理为结构化摘要，新摘要、任务完成状态和会话上下文版本一起保存成功；之后模型使用新摘要加最近消息，不再重复携带被摘要覆盖的原文。
- **包含的后续动作**：普通路径先在 MySQL 创建任务，再用 Kafka 通知消费者；消费者失败时进入重试主题，耗尽次数后保存为不可再自动执行的失败状态。工具调用前的紧急整理在当前请求线程中完成，或等待另一执行者最多 5 秒。

### 文字链路

```text
助手回答保存到 MySQL
-> 记忆服务读取当前长期摘要已经覆盖到的消息序号
-> 统计该序号之后到本次助手回答之间的有效消息 Token
   - 少于 12000 Token -> 本轮不创建整理任务
   - 达到 12000 Token -> 读取这段尚未整理的完整消息
-> 从最新消息向前保留约 4096 Token，避免刚发生的对话立刻只剩摘要
-> 把更早消息确定为本次需要整理的连续序号范围
-> 对范围内消息编号、有效状态、正文和附件内容计算 SHA-256 摘要，用来识别整理期间输入是否发生变化
-> 使用会话、消息范围、摘要版本、上下文版本、内容摘要和策略版本生成稳定任务键
-> 先在 MySQL 创建任务
   - 相同任务再次创建 -> 数据库唯一键返回原任务，不重复生成摘要
   - 初始状态为 PENDING，attemptCount 为 0
-> 再向 Kafka topic context.compaction.request.v1 发送一条任务通知
   - 分区键：tenantId:sessionId，同一会话的通知尽量保持顺序
   - Kafka 只提醒消费者“有任务可做”，最终任务状态以 MySQL 为准

Kafka 消费组 ai-agent-context-compaction 收到通知
-> 从消息恢复租户、用户和原始 traceId，后台日志继续属于同一次业务过程
-> 用条件更新领取 MySQL 任务
   - 任务已经完成、取消或被其他实例领取 -> 本次通知直接结束，不重复生成摘要
   - 领取成功 -> attemptCount 加 1，取得 60 秒执行期限并推进本次执行编号
-> 再次读取当前摘要、会话上下文版本、消息和附件
-> 对比任务创建时保存的摘要版本、上下文版本和内容 SHA-256
   - 另一任务已经覆盖同一范围 -> 当前任务直接完成，不再调用模型
   - 用户取消、追加要求或消息有效性发生变化 -> 拒绝使用旧输入生成的结果
-> 根据会话所用 Agent 找到对应模型
-> 把旧摘要、待整理消息、附件和明确 JSON 格式要求交给模型
-> 模型返回 conversationSummary、confirmedDecisions、constraints、openItems、keyEntities
-> 服务端校验这些字段并自行写入准确的消息起止范围，不信任模型自报的范围
-> 模型调用结束后再次检查任务状态、会话上下文版本和本次执行编号
-> 在一个短数据库事务中完成以下更新
   1. 锁定当前会话记录，防止同时修改上下文
   2. 再次确认消息和附件内容没有变化
   3. 保存新摘要并把旧摘要改为不再使用
   4. 将任务改为 SUCCEEDED
   5. 推进会话 contextRevision，通知后续模型调用背景信息已经变化
-> 事务成功后才更新 Redis 摘要，并删除已经进入摘要的近期消息
-> 后续模型调用读取“新长期摘要 + 尚未覆盖的最近消息”

处理失败
-> 先把错误原因写回 MySQL 任务
-> 未达到最多 3 次 -> 状态改为 RETRYING，并由 Kafka 重试主题延迟 1000ms 再次通知
-> 达到最多 3 次，或 Kafka 重试链耗尽进入 DLT -> 状态改为 DEAD，保留错误供排查

模型已决定调用工具，但执行前发现上下文超过整理阈值
-> 当前请求先创建或找到同一范围的任务
-> 当前线程领取成功 -> 立即执行上述摘要生成和激活过程
-> 已被另一个消费者领取 -> 最多等待 5 秒，每次等待从 50ms 开始逐步增加，最大 1000ms
-> 新摘要成功激活 -> contextRevision 已变化，本次工具参数基于旧背景生成，拒绝直接执行并要求模型重新判断
-> 等待超时或整理失败 -> 工具不在旧背景下继续执行，当前调用按明确错误结束
```

### 关键控制点

- **任务先保存、通知后发送**：即使 Kafka 重复投递，数据库任务键和领取条件也能阻止重复摘要。
- **异步阈值**：默认尚未整理历史达到 12000 Token 才创建任务，并保留最近约 4096 Token 原文。
- **重复执行保护**：摘要版本、会话上下文版本、内容 SHA-256 和任务本次执行编号共同阻止过期结果覆盖新对话。
- **模型调用不占用数据库长事务**：耗时的模型请求在事务外完成，最后只用短事务保存经过再次核对的结果。
- **工具执行前重新判断**：如果整理导致背景信息版本变化，旧背景下生成的工具参数不会继续执行。
- **后台重试有上限**：任务和 Kafka 都默认最多尝试 3 次，最终失败会在 MySQL 中留下明确状态。

### 当前实现审查

**已经达到的效果**

- 助手回答保存后可以按阈值创建任务，把较早历史交给 Kafka 后台整理。
- 同一任务重复创建或重复通知不会重复激活摘要。
- 摘要生成前后有多层版本和内容检查，能阻止取消、消息变化或并发任务产生的旧结果覆盖新上下文。
- 工具调用前支持同步整理；摘要变化后会要求模型基于新上下文重新选择工具和参数。
- 新摘要激活、旧摘要停用、任务完成和会话上下文版本推进处于同一事务。

**修正后需要保留的边界**

- Kafka 发布端会等待确认；发送失败时明确报错，但不会推翻已经保存成功的助手回答，MySQL 任务继续保留。
- 定时扫描会查找等待处理、等待再次尝试和处理超时的任务并重新通知；单条通知失败不会阻止同批其他任务。
- **Kafka 开发配置默认关闭。** `AI_CONTEXT_KAFKA_ENABLED` 默认值是 `false`。因此“Kafka 异步整理”只有部署时明确开启监听器并准备好 topic、retry topic 和 DLT 才真实运行。
- **同步整理范围需要准确描述。** 生产代码只在模型已经决定调用工具、真正执行工具之前调用 `compactBeforeTool`；普通模型调用前没有同步整理，只会按预算选择近期消息。`compactSynchronously` 没有生产调用点。
- 同一会话再次产生回答时会顺手通知该会话未完成任务；全局定时扫描负责覆盖长期不活跃的会话。

### 未展开的外部边界

- **摘要模型**：代码可以确认输入、JSON 输出约束、服务端校验和失败行为，但不推断模型内部如何概括对话。
- **Kafka 服务端**：代码可以确认 topic、分区键、消费组和重试设置；未连接共享环境验证 topic 实际创建情况和消息保留策略。

## 10. 用同一个 Trace ID 串起同步与后台处理日志

### 链路范围

- **入口**：任意 HTTP 请求进入应用；客户端可以携带 `X-Trace-Id`，没有携带或内容不安全时由服务端生成新的编号。
- **完成标志**：HTTP 响应返回该编号，当前请求产生的运行记录、消息、模型调用、工具调用、RAG 检索和工作流事件都能带上同一个编号；后台线程或 Kafka 消费者继续使用原编号记录后续步骤，并在结束时清理线程数据。
- **包含的后续动作**：工作流后台线程、线程池任务、RAG 入库任务和上下文摘要 Kafka 消费者。

### 文字链路

```text
HTTP 请求进入 TraceIdFilter
-> 读取请求头 X-Trace-Id
   - 只允许 1 到 64 位字母、数字、点、下划线、冒号和短横线
   - 没有提供、过长或包含换行等不安全字符 -> 服务端生成 UUID
-> 把最终编号放入当前线程和日志上下文
-> 同时写入 request attribute，保证统一异常处理仍能找到它
-> 在响应头写回 X-Trace-Id，并允许浏览器跨域读取这个响应头
-> 认证过滤器继续把 tenantId、userId 放入同一个日志上下文
-> 控制器和领域服务开始处理业务

创建 Chat Run 或智能工作流运行
-> 将当前 Trace ID 保存到 chat_run.trace_id
-> 用户消息和助手消息保存时沿用 Run 的 Trace ID，并写入 chat_message.trace_id
-> ChatService 准备调用 Agent
-> 把 Trace ID 写入 ADK 的只读运行状态
-> 模型调用日志插件从当前线程和运行状态记录同一编号
-> Agent 决定调用工具
-> GatewayAdkTool 从服务端运行状态恢复 Trace ID，不接受模型通过参数修改它
-> Tool Gateway 的开始、成功、失败审计和工作流工具事件都保存该编号
-> Agent 调用 RAG
-> 检索请求、各阶段候选审计和最终引用记录继续保存该编号
-> 工作流每个节点开始、结束、路径选择和最终路径事件继续使用 Run 中保存的编号

业务切换到后台线程
-> 提交任务前复制当前 Trace ID、租户和用户信息
-> 工作线程开始执行时把这些值放入自己的线程上下文
-> 智能工作流额外明确使用 Run 中保存的根 Trace ID，避免后续查看请求的编号替换原运行编号
-> 后台步骤记录日志
-> 任务结束后恢复线程原有内容，防止线程复用时把上一个用户的编号带到下一个任务

业务通过 Kafka 延后处理
-> 生产者把 Trace ID 作为任务字段写入数据库记录和 Kafka 消息
-> 消费者收到消息后从可信任务字段恢复 Trace ID 和租户身份
-> 消费者回查 MySQL 任务并执行真实业务
-> 后台日志继续使用原编号
-> 消费结束后清理 Trace ID、租户信息和 MDC，防止同一 Kafka 线程处理下一条消息时串到上一条链路

请求结束
-> 普通 JSON 业务响应的响应体自动补充 traceId
-> Spring 统一错误响应也从 request attribute 读取同一个 traceId
-> 记录 HTTP 状态和耗时
-> 清理当前 HTTP 线程的 Trace ID 与租户信息
-> 用户可以拿响应中的编号查询这次业务过程的日志
```

### 关键控制点

- **外部编号先校验**：请求头只能使用有限字符且最多 64 位，避免有人通过换行污染日志或构造超长查询条件。
- **运行编号与查看请求编号分开**：Run 保存首次启动时的根 Trace ID；之后订阅 SSE 或查询状态的 HTTP 请求有自己的操作编号，但返回数据仍明确给出 Run 的根编号。
- **跨线程显式复制并清理**：线程池会复制 Trace 和租户信息；智能工作流使用 Run 根编号包装执行任务；任务完成后恢复线程原状态。
- **跨 Kafka 显式写入消息**：后台消费者不能依赖 HTTP 线程变量，必须从消息中的任务字段恢复。
- **业务记录也保存编号**：即使日志已经滚动，Run、消息、工具审计、工作流事件和 RAG 审计仍能提供关联编号。

### 当前实现审查

**已经达到的效果**

- HTTP 入口、正常响应和异常响应使用同一 Trace ID，并能安全接收调用方提供的编号。
- Chat Run、消息、工具、RAG 和工作流事件都存在明确的 Trace ID 保存或传递代码。
- 智能工作流线程和 Kafka 上下文摘要消费者会显式恢复并清理 Trace ID。
- 日志格式把 Trace ID 作为日志正文中的字段，而不是 Loki 高基数标签，适合按字段查询且不会制造大量标签组合。

**需要修正或明确的地方**

- “全链路”目前由多种机制共同保证，不是统一的 OpenTelemetry Trace；没有 `spanId`、父子调用关系或跨服务 W3C `traceparent` 协议。准确说法应是“项目级业务 Trace ID 透传”。
- 普通线程池只有使用 `TraceableThreadPoolExecutor` 才会自动复制上下文；后续若新增原生线程、第三方异步回调或新的 Kafka 消费者，仍需显式接入，当前机制不能自动覆盖未来所有异步代码。
- 文件日志使用异步队列且设置 `neverBlock=true`，应用繁忙、队列满时日志可能被丢弃。数据库中的业务记录仍在，但不能保证 Loki 中每个步骤永远完整。
- 已核对本地 Alloy 配置会采集应用日志；远端 Loki 的采集、保留和 Grafana 数据源属于部署边界，未连接共享环境验证当前在线状态。

## 11. Cobra CLI 查询 Grafana/Loki 并分析日志

### 链路范围

- **入口**：人工或具备本机命令执行能力的 Agent 运行 `grafana-log trace <trace-id>`；也可以按 runId、sessionId、retrievalId 或入库 taskId 查询。
- **完成标志**：CLI 输出按时间排列且已脱敏的日志，并汇总失败、降级、取消、耗时较长和只有开始没有结束的阶段；调用方据此定位业务在哪一步异常。
- **包含的后续动作**：没有消息队列。CLI 同步调用 Grafana 健康检查、数据源查询或 Loki 范围查询接口；无结果时可以逐步扩大时间范围。

### 文字链路

```text
用户或具备命令执行能力的 Agent 运行 grafana-log trace <trace-id>
-> Cobra 校验必须且只能提供一个 Trace ID
-> 从当前项目向上查找本机 codex.md
-> 只读取 grafana-log-cli-config-v1 标记范围内的 JSON 配置
-> 校验 Grafana URL、Loki datasource UID、认证方式、默认查询范围和超时
   - 用户名、密码或 Token 只允许来自本机配置块
   - 命令行和环境变量不能覆盖认证信息，避免凭据进入 shell 历史
-> 校验结果数量和单页数量
   - 总量最多 100000 行
   - 单页最多 5000 行
   - 查询时间最多 31 天
-> 将 Trace ID 构造成精确 LogQL
   - 先用字面字符串 traceId=<值> 缩小日志
   - 再用 logfmt 解析并确认 traceId 字段完全相等，避免部分字符串误命中
-> 只向 Grafana datasource proxy 发 GET 请求，不直接连接 Loki，也不调用任何写接口
-> Grafana 将请求转发给指定 Loki 数据源的 query_range 接口
-> CLI 按时间位置逐页查询并对“时间戳 + 标签 + 日志正文”去重
   - 分页位置无法继续前进 -> 明确报错，不悄悄遗漏同一时间点的大量日志
   - 网络错误、限流或 5xx -> 最多尝试 3 次，等待 200ms、400ms，服务端 Retry-After 优先，单次等待最多 3 秒
   - 响应超过 16 MiB -> 停止读取并报错
-> 默认 30 分钟没有找到 Trace ID
   - 自动扩大到 2 小时、12 小时、24 小时、72 小时
   - 找到第一批结果后停止继续扩大
-> 将每条日志解析为时间、级别、事件、阶段、结果、耗时、错误码和业务编号
-> 对正文和错误信息执行脱敏处理
-> 按时间排序并生成证据摘要
   - errorCode、ERROR、failed 或 success=false -> 归为失败记录
   - degraded -> 归为降级记录
   - cancelled 或取消事件 -> 归为取消记录
   - 统计耗时最长的 10 个阶段
   - 有 started 但没有完成、失败或取消记录 -> 标记为“只看到开始，没有看到结束”
   - 有输入和输出数量 -> 形成 RAG 候选数量变化
-> 输出结果
   - timeline：中文时间线，供人直接阅读
   - jsonl：先输出查询信息，再逐条输出日志，最后输出分析摘要，适合 Agent 继续判断
   - table/json/raw：用于表格查看、程序处理或检查脱敏后的原始行
-> 调用方依据日志证据说明失败位置、降级原因和缺失步骤，不把“没有日志”直接当成业务一定失败
```

### 关键控制点

- **只读边界**：客户端只有 GET 请求，查询经 Grafana 的 Loki 数据源代理完成，不提供删除日志、修改数据源或看板的命令。
- **认证信息不进入参数**：敏感配置只能来自本机 `codex.md` 的限定 JSON 区块，错误输出还会再次脱敏。
- **查询范围有硬上限**：最多 31 天、100000 行、单页 5000 行、单次响应 16 MiB，防止 Agent 发起无界查询。
- **自动扩大时间只用于 Trace ID**：默认从 30 分钟开始，无结果才逐步扩大，最大 72 小时。
- **分析只报告可观察事实**：CLI 能识别错误、降级、取消、慢阶段和缺失结束记录，但不会凭空断定根因。

### 当前实现审查

**已经达到的效果**

- Cobra CLI 已实现 `trace/run/session/retrieval/ingest/search/query/doctor` 命令，并有查询边界、只读 HTTP 客户端、分页、重试、脱敏和多种输出格式。
- `trace` 命令能按 Trace ID 精确过滤并自动扩大时间范围。
- CLI 能输出机器可读的 JSONL 分析结果，Skill 包也包含多平台二进制、SHA-256 清单、安装脚本和自检脚本。

**修正后的双入口**

- 平台新增 `query_trace_logs`：功能开关开启后，运行中的 Agent 只能查询当前运行自己的 Trace ID，最多回看 120 分钟、返回 500 行，不能提交任意 LogQL。
- 日志 Skill 已增加平台工具调用说明；但仓库文件不能证明它已经上传、发布并绑定到线上 Agent，因此简历应把“Skill 提供分析方法”和“平台工具提供受控查询”分开陈述。
- 开发者继续使用 Cobra CLI，支持 Trace ID、runId、sessionId、retrievalId 等多种编号，以及分页、重试和自动扩大时间范围。这些 CLI 能力不能泛化成平台工具也全部具备。
- CLI 的 `query` 命令只做长度、空值和 NUL 校验。LogQL 本身是查询语言且客户端只发 GET，但若希望把它直接暴露给平台 Agent，仍应禁用原始 `query`，只开放 `trace/run/...` 等受控命令，避免昂贵或越权的宽范围查询。

### 未展开的外部边界

- **Grafana、Loki 和日志采集器**：代码能确认请求协议和本地采集配置，但远端服务的数据完整性、保留时间与权限配置需要部署环境验证。

## 12. 将 PDF、DOCX 和 Markdown 转成统一文档结构

### 链路范围

- **入口**：管理员向知识库上传 PDF、DOCX 或 Markdown 文件，上传接口返回文档编号、版本编号和入库任务编号。
- **完成标志**：后台 Worker 产出一份统一的 `Document IR`，其中正文、标题、表格、页眉页脚、来源位置和阅读顺序使用相同数据结构表示；同时保存原始解析结果、统一结构、展示用 Markdown 和质量报告。
- **包含的后续动作**：Outbox 定时发布 Kafka 通知，Kafka 消费者或数据库定时扫描唤醒 Worker；Worker 下载原文件并按格式选择解析器。

### 文字链路

```text
管理员上传 PDF、DOCX 或 Markdown
-> 服务端确认当前用户可以管理目标知识库，且知识库处于可接收文档状态
-> 检查文件类型、大小、文件名和真实内容特征
-> 生成 documentId、不可修改的 versionId、taskId 和 Outbox eventId
-> 先把原文件流式写入 MinIO，并由服务端计算内容 SHA-256
-> 用“租户 + 知识库 + 内容 SHA-256”生成重复上传判断键
   - 相同内容已经有任务 -> 删除本次多余文件，返回原任务，不重复解析和向量化
-> 在一个数据库事务中保存逻辑文档、文档版本、摄取任务和 Outbox 事件
-> 接口返回 queued，上传请求结束；解析在后台继续

Outbox 每隔 1 秒扫描待发送事件
-> 领取一条事件并取得本次发布编号
-> 向 Kafka topic rag.ingest.request.v1 发送任务编号
-> 等待 Kafka 明确确认
   - 确认成功 -> 把 Outbox 事件改为 published
   - 超时或失败 -> 按带随机浮动的指数间隔再次发送，达到上限后保存为 dead

Kafka 消费者收到任务编号，或者 Worker 每隔 2 秒从 MySQL 扫描到未完成任务
-> 提交到单线程有界队列
   - 同一任务已经在本实例排队 -> 忽略重复通知
   - 队列已满 -> 不丢任务，等待下一次数据库扫描
-> Worker 从 MySQL 领取任务，取得 3 分钟执行期限和本次执行编号
-> 后台每 30 秒延长执行期限；每个外部调用前再次确认任务没有被取消且仍由当前 Worker 持有
-> 把文档版本改为 processing，并记录本次解析器和 Embedding 模型版本
-> 从 MinIO 下载原文件到只属于本次任务的临时目录
-> 核对文件大小和 SHA-256，防止对象被替换或下载不完整

按 MIME 类型选择独立解析过程
-> Markdown
   -> 在本地按 UTF-8 有界读取
   -> 使用 CommonMark AST 识别标题、正文、列表、表格、代码、引用和源码字符范围
-> DOCX
   -> 默认使用 Apache POI 读取 OOXML，不依赖版面转换服务
   -> 按文档中的段落和表格出现顺序读取正文
   -> 根据 Heading/标题样式和 outline level 恢复一到六级标题路径
   -> 表格保留行、列、横向合并和可识别的纵向合并信息
   -> 页眉、页脚和脚注作为独立类型保存，不混入普通正文
   -> 本地解析失败 -> 改用 Docling，并记录发生了降级
-> PDF
   -> 以流式 multipart 上传到 Docling，同时请求 Markdown 和结构化 JSON
   -> 关闭图片回传，限制最大页数、文档大小、并发数和总超时
   -> 从 Docling provenance 恢复每个内容块的页码、边界框和页内顺序
   -> 映射标题、正文、列表、表格、代码、公式、图片说明、页眉页脚和 OCR 标记

所有格式转换成同一个 Document IR
-> 每个块保存稳定 blockId、内容类型、原文、规范化文本、标题路径和阅读顺序
-> 能取得页码和坐标时保存页码、边界框；能取得源码范围时保存字符起止位置
-> 表格保存为行和单元格结构，不只保留一段制表符文本
-> 清理重复页眉页脚、断行和可识别版面噪声，并保留清理审计
-> 计算文本覆盖率、乱码、空页、OCR、标题和表格等质量指标
   - 主解析质量不足且允许 OCR -> 再用强制 OCR 解析一次，比较两次质量后选较好结果
   - 质量需要人工查看 -> 保存解析产物和质量报告，但停止后续向量写入
   - 质量不能接受 -> 保存失败证据，不让文档进入检索
-> 把以下产物写入 MinIO
   - parsed/parser-output.json：解析器原始结构化输出
   - ir/document-ir-v1.json：平台统一文档结构
   - normalized/normalized.md：供查看的规范化文本
   - quality/quality-report.json：解析质量与告警
-> 在任务进度中保存主产物对象键、SHA-256 和大小
-> 后续步骤若进程退出，可以从已保存产物恢复，不必重新调用解析服务
```

### 关键控制点

- **原文件版本不可修改**：对象路径包含租户、知识库、文档和版本；后续重传生成新版本，不覆盖正在使用的原件。
- **任务登记和通知可靠分开**：文档、版本、任务和 Outbox 同事务保存；Kafka 只是加快唤醒，MySQL 定时扫描可以接手漏掉的通知。
- **不同格式不强行走同一解析器**：Markdown 使用本地 AST，DOCX 优先本地 OOXML，PDF 使用 Docling 版面结构。
- **中间结构统一**：格式差异在解析阶段消化，清洗、切块和入库只读取统一 Document IR。
- **质量不合格不能进入搜索**：先保存可核对的解析和质量产物，再停止后续索引动作。
- **取消和多实例抢占受控**：每个外部调用前核对任务持有者、执行编号和取消状态，旧 Worker 不能继续写入。

### 当前实现审查

**已经达到的效果**

- PDF、DOCX、Markdown 确实采用不同解析过程，并统一输出 Document IR。
- PDF 可以从 Docling JSON 保留页码、边界框和页内阅读顺序；DOCX 可以保留标题层级、正文/表格顺序和 OOXML 表格结构。
- 解析、统一结构、展示文本和质量报告作为独立对象保存，任务可以从中间产物继续。
- Outbox 等待 Kafka 确认，Worker 还有数据库定时扫描，不依赖单次消息必达。

**需要修正或准确表述的地方**

- **DOCX 没有可靠页码。** DOCX 是流式排版格式，本地 Apache POI 解析器明确写入 `DOCX_PAGE_NUMBER_UNAVAILABLE_WITHOUT_CONTROLLED_RENDERER`，`pageCount` 返回 0。简历不能笼统写“所有格式都保留页码”，应写“保留标题、表格和阅读顺序，PDF 额外保留页码与版面位置”。
- Docling 遇到网络错误或 5xx 会立即再请求一次，最多请求两次；完整请求超时、4xx 和非法响应不会在适配器内重复请求，之后由 Worker 判断是稍后整体重试还是直接失败。
- PDF 的标题路径和阅读顺序依赖 Docling 返回的结构化 provenance；缺少该信息时只能按可验证数据降级，不能保证每份复杂扫描件都完全还原原版面。
- Worker 质量门禁的具体阈值和 OCR 选择受部署配置影响；简历应描述“有质量检查和 OCR 兜底”，不能承诺所有低质量文件都会自动修复成功。

### 未展开的外部边界

- **Docling**：代码能确认请求参数、结构映射和失败处理，不推断其内部版面模型和 OCR 算法。
- **MinIO 与 Kafka**：只陈述代码中的对象键、确认和恢复语义，未连接共享环境核对当前部署状态。

## 13. 从统一文档结构生成父子分块并启用新索引版本

### 链路范围

- **入口**：文档已经完成格式解析、统一结构转换和质量检查，摄取任务进入切块阶段。
- **完成标志**：父块和子块保存到 MySQL，子块的 Dense/Sparse 向量分批写入 Qdrant，数量核对通过后，在同一个数据库事务中把新文档版本和索引代次设为可检索并结束任务。
- **包含的后续动作**：Embedding、Sparse 编码、Qdrant 写入、数量校验，以及失败重试或终态清理。

### 文字链路

```text
Worker 从已校验的 Document IR 开始切块
-> 按页码和 readingOrder 读取可检索内容块
-> 删除标题、页眉、页脚、页码和水印本身，但把当前标题路径保留为正文上下文
-> 普通正文按标题边界合并
   - 子块同时受 1800 字符和约 420 Token 上限控制
   - 超长正文优先在句末或空白处分开，并保留约 160 字符重叠
-> 表格单独处理
   - 重复表头到每一组数据行，保证一个小块单独命中时仍知道各列含义
   - 表格、代码、公式和图片说明不与相邻正文混在同一子块
-> 为每个子块生成两份文本
   - displayText：保留用于引用展示的正文
   - embeddingText：只在向量化副本前加入“文档标题 + 章节路径 + 正文”，提高脱离上下文的小块召回率
-> 同一章节内的相邻子块继续合并成父块
   - 父块同时受 6000 字符和约 1400 Token 上限控制
   - 标题路径变化时立即开始新的父块
-> 为父块和子块生成由版本、顺序和内容 SHA-256 决定的稳定 chunkId
-> 子块记录 parentChunkId，并按全文顺序记录 previousChunkId 和 nextChunkId
-> 每个块保存页码范围、标题路径、来源 blockId、来源位置、内容摘要和质量标记
-> 保存 chunk-manifest.json，并把父子块完整写入 MySQL

开始向量入库
-> 只选择 CHILD 子块参与搜索，父块不写入召回候选
-> 取 Embedding 批量和 Qdrant 批量配置中的较小值作为每批数量
-> 每一批先检查任务仍可执行并延长执行期限
-> 把 embeddingText 发送给 Embedding 服务生成 Dense 向量
-> 使用项目内固定 Sparse 编码器生成 Sparse 向量
-> 将 Dense、Sparse 和以下可信过滤字段一起写入 Qdrant
   - knowledgeBaseId、documentId、versionId、generation、chunkId
   - headingPath、pageNumber、contentHash
-> 每批成功后把已处理子块数、批次编号和向量写入位置保存到 MySQL
-> 进程中断后从最后成功位置继续，不重新处理已确认批次

所有子块写入完成
-> 查询 Qdrant 中当前文档版本和 generation 的向量数量
-> 与 MySQL 子块数量逐项核对
   - 数量不一致 -> 不启用新版本，任务进入可重试或失败处理
-> 从 MinIO 重新读取 Document IR 主产物并核对对象键、大小和 SHA-256
-> 在一个数据库事务中完成四项更新
   1. 将文档版本改为 READY，保存页数、字符数、分块数、解析器和质量元数据
   2. 将逻辑文档的 activeVersionId 和 activeGeneration 指向新版本
   3. 将知识库 currentGeneration 更新为本次代次
   4. 将摄取任务改为 COMPLETED 并释放执行期限
-> 只有事务全部成功，新版本才进入检索范围
-> 检索服务之后只读取 activeVersionId 和 currentGeneration 对应的块和向量

处理失败
-> 判断是网络抖动等暂时错误，还是文件非法等不可恢复错误
-> 暂时错误且未达到 3 次 -> 按 5 秒起、最长 5 分钟的指数间隔再次执行，并从任务已保存的阶段继续
-> 不可恢复或次数耗尽 -> 删除本版本已写入的 Qdrant 向量和 MySQL 分块，再保存 FAILED/DEAD 与错误码
-> 取消任务 -> 清理本版本派生向量、分块和解析产物，旧的活动版本不受影响
```

### 关键控制点

- **小块用于搜索，父块用于补语义**：只有子块向量化；检索命中后再根据 `parentChunkId` 和相邻指针补充上下文。
- **展示文本和向量文本分离**：章节标题可以帮助搜索，但引用展示仍使用原始正文，避免把人为添加的前缀伪装成文档原文。
- **每批保存进度**：外部向量写入和数据库进度按批推进，进程退出后可以从已确认位置继续。
- **先核对再启用**：Qdrant 数量、MySQL 子块和 MinIO 产物都通过检查后，才切换活动版本。
- **启用动作在一个事务中**：版本、文档、知识库代次和任务必须一起成功，检索不会看到只完成一半的新版本。
- **失败不会污染旧版本**：失败或取消只清理目标版本，新版本未启用前，查询仍使用原活动版本。

### 当前实现审查

**已经达到的效果**

- Document IR 切块器保留标题边界、表格结构、阅读顺序、页码范围和父子/相邻关系。
- 子块的检索文本会加入文档标题和章节路径，展示文本保持原样。
- Dense 和 Sparse 向量分批写入，进度保存到 MySQL，并在启用前核对数量和不可修改的 IR 产物。
- 文档版本、逻辑文档、知识库当前索引批次和任务在一个事务中完成切换。
- Worker 会定时延长任务处理时限、检查取消状态；处理超时后可由其他 Worker 接手，并支持定时扫描、逐步增加等待时间的重试和最终失败清理。

**需要修正或准确表述的地方**

- 分块 Token 使用项目内字符近似算法，不是实际 Embedding 模型 tokenizer；产物已经记录 `TOKENIZER_APPROXIMATION_ACTIVE`。简历可以写“双重长度预算”，不能说按模型精确 Token 切块。
- Sparse 是确定性的项目内编码器，不是训练型稀疏模型。该限制和第 7 条检索审查一致。
- 配置项写的是字符和近似 Token 上限；上述 1800/420、6000/1400、160 是开发环境默认值，部署可通过环境变量改变。
- 父块和相邻块是在检索返回阶段补入上下文，不是全部向量化。简历中“小块向量化、父块保留章节语义”是准确的。

### 未展开的外部边界

- **Embedding 与 Qdrant**：代码能验证批量输入、向量数量、过滤字段、重试和启用条件，不说明外部模型内部如何生成向量。

## 14. 用固定问题集比较检索策略并计算指标

### 链路范围

- **入口**：运行 Benchmark CLI，指定已经准备好的 SciFact 成对 PDF/DOCX 数据集、固定随机种子、目标格式和预处理策略。
- **完成标志**：200 个问题分别通过 Dense、Sparse、Hybrid RRF、Hybrid RRF + Rerank 四种配置完成 800 次查询；每次结果和运行清单写入文件，再与标准相关文档列表对比，生成 Recall、MRR、nDCG、MAP、耗时和候选数量报告。
- **包含的后续动作**：先上传并等待 200 份文档可检索，再创建四套检索配置和工作流；正式查询前执行预热检查，全部正式查询通过单条结果检查后才评分。

### 文字链路

```text
Benchmark CLI 读取准备好的 SciFact 格式数据集
-> 校验数据集清单、文档、问题、标准相关文档列表和 document map 都存在
-> 使用固定 seed=20260729 打乱 200 个问题，保证不同策略使用相同问题但降低固定顺序偏差
-> 为目标格式创建独立知识库
-> 逐个上传 200 份 PDF 或 DOCX，并等待每份文档完成解析、切块、向量化和版本启用
-> 核对任务已完成且文档确实处于可检索状态
-> 创建四套检索配置
   - dense：只使用 Dense 向量
   - sparse：只使用 Sparse 向量
   - hybrid_rrf：Dense 和 Sparse 候选按 RRF 合并
   - hybrid_rrf_rerank：RRF 合并后再使用 Rerank 调整前 10 个候选顺序
-> 每套配置创建独立已发布工作流并绑定同一知识库
-> 保存 profile、binding 和 target 编号，保证每条结果能还原实际配置

正式评测前先运行少量预热问题
-> 四种策略都必须返回合法结果
-> 任一预热出现业务错误、降级、空排名、重复组合或 Rerank 没有实际候选/耗时 -> 停止评测，不创建正式结果文件

开始 200 × 4 次正式查询
-> 每个问题按轮换顺序调用四种策略，避免某一种策略总在相同时间位置运行
-> 调用真实 RAG 调试接口，保存 retrievalId、前 10 个文档编号、总耗时、阶段耗时、候选数量和降级原因
-> 每条结果写入前立即检查
   - 有业务错误、发生降级、结果为空或结构不合法 -> 当前评测失败，不能把坏结果混入平均值
-> 每完成一条追加到 run.jsonl，支持中断后按已完成数量继续
-> 最终每种格式必须恰好有 800 条：每种策略 200 条

读取 qrels 中每个问题的标准相关文档
-> 按 queryId 对齐每种策略返回的文档排名
-> 缺少某个问题的运行结果 -> 按空排名计分，并增加 missingRunCount，不用已有样本掩盖缺失
-> 同一问题排名里出现重复文档 -> 拒绝评分
-> 对每个问题计算
   - Recall@1/5/10：前 1、5、10 个结果覆盖了多少标准相关文档
   - MRR@10：第一个相关文档出现得越靠前分数越高
   - nDCG@10：同时考虑相关性等级和排序位置，再与理想顺序比较
   - MAP@10：前 10 个位置每次命中时的精确率平均值，未召回的相关文档会降低分数
-> 对 200 个问题取平均，生成每种策略的指标和逐问题明细
-> 生成 run-manifest.json 和 metrics.json，保存代码版本、配置摘要、数据集摘要、结果摘要、错误数、降级数和完成数量
```

### 指标核对

当前简历引用的是 **Dense** 策略，不是四种策略中的最佳值：

| 格式 | 问题数 | 缺失结果 | Recall@1 | Recall@5 | Recall@10 | nDCG@10 |
|---|---:|---:|---:|---:|---:|---:|
| PDF / IR_FULL | 200 | 0 | 82.5% | 93.5% | 96.0% | 0.897501 |
| DOCX / IR_FULL | 200 | 0 | 83.5% | 95.0% | 96.0% | 0.904045 |

两次运行均使用数据集 `scifact-paired-pdf-docx-200-v1`、相同数据集摘要、相同配置摘要和相同代码版本；每次包含 200 份文档、800 条正式查询结果，运行清单状态为 `completed`，错误、降级和空结果均为 0。

### 关键控制点

- **格式对比使用同一问题集**：PDF 和 DOCX 清单中的数据集摘要、配置摘要、代码版本和随机种子一致，只改变文档格式和各自独立知识库。
- **四种策略使用同一批 200 个问题**：每种策略恰好 200 条，避免样本数量不同造成不可比。
- **坏运行不能悄悄参与平均**：预热和每条正式结果都有检查；缺失结果在评分时按空结果处理，不会只对成功样本求平均。
- **指标实现不调用大模型**：评分由确定性的 Java 代码根据 qrels 和文档排名计算，可重复核对。
- **运行证据可追溯**：清单保存数据集、配置、代码和结果 SHA-256，指标文件保留每个问题的明细。

### 当前实现审查

**已经达到的效果**

- Benchmark 模块可以准备数据、上传文档、创建四种检索配置、预热、执行真实查询、继续中断运行并独立评分。

## 第一轮结论与修正结果

十四条证据链已经完成源码审查，能够闭环说明工作流、工具、RAG、会话记忆、Trace 日志、文档入库和评测结果。第一轮发现的实现问题已经按简历目标修正：

1. Agent 节点对可能恢复的失败默认最多尝试 3 次，等待时间逐次增加；每次尝试使用独立的执行编号和调用记录。
2. 后台线程池拒绝工作流任务时，运行会立即写入失败状态和失败事件，不再长期停在 `RUNNING`。
3. MCP 和 Skill 都进入节点执行计划，普通 DAG 与智能工作流都会按当前节点配置过滤工具。
4. Redis 近期消息必须连续覆盖所需序号范围；前半段被裁掉、结尾不足或中间缺号时回查 MySQL。
5. Kafka 发布端等待发送确认；发送失败时数据库任务继续保留，定时扫描会再次通知未完成任务。
6. 新增 `query_trace_logs` 平台工具，Agent 只能查询当前运行自己的 Trace ID，不能提交任意 LogQL；Cobra CLI 继续供开发者使用。
7. Docling 遇到网络错误或 5xx 会再请求一次；完整请求超时、4xx 和响应格式错误不会盲目重试。

仍需通过准确措辞保留的边界是：RAG 调用预算和证据只在当前 Java 进程内累计；非法引用只记录、不阻止回答；平台没有独立的问题自动改写器；DOCX 不保证页码；评测只评价检索排序，且本次 Hybrid/Rerank 没有超过 Dense。

| 问题 | 修正后的效果 | 验收证据 |
|---|---|---|
| Agent 偶发调用失败 | 只对可能恢复的错误逐次增加等待时间并再次尝试；每次尝试单独记录，次数耗尽后只走当前节点合法的失败出口 | 节点重试、取消期间停止等待、失败出口测试 |
| 后台执行任务提交失败 | 线程池拒绝任务时立即写入运行失败状态和结束事件 | 线程池拒绝、运行状态和事件测试 |
| 节点工具范围 | MCP 与 Skill 都按当前节点配置过滤，普通 DAG 和智能工作流使用同一边界 | 计划编译、动态工具清单和执行前授权测试 |
| Redis 近期消息完整性 | 所需消息序号必须连续；缓存缺少任何一段时回查 MySQL | 缓存窗口裁剪、缺号和 MySQL 回退测试 |
| Kafka 摘要任务通知 | 等待 Kafka 确认；数据库扫描会再次通知没有处理完的任务 | 发布失败、全局扫描和重复通知测试 |
| Agent 查询日志 | `query_trace_logs` 只查询当前运行，限制 120 分钟和 500 行，服务端固定生成查询 | 参数权限、工具发现和 Grafana 只读协议测试 |
| Docling 5xx 重试 | 网络错误或 5xx 再请求一次；超时、4xx 和非法响应不重试 | 5xx、网络错误、超时、4xx 和非法响应测试 |

### 不应扩大实现，直接把简历说准确

| 容易写过头的说法 | 准确说法 |
|---|---|
| 所有文档都保留页码 | 保留标题、表格和阅读顺序；PDF 额外保留页码和版面位置，DOCX 在没有固定渲染器时不保证页码 |
| 每轮调用模型前都会同步压缩历史 | 模型已经决定调用工具、真正执行工具前，如果上下文超过阈值，会先同步整理较早历史 |
| 实现了完整分布式 Trace | 统一生成并传递项目级 Trace ID，将请求、运行、工具、RAG 和后台任务的记录关联起来 |
| 评测证明回答正确 | 评测证明相关文档的检索位置；没有标准答案，因此没有评价最终回答质量 |
| Hybrid 和 Rerank 一定优于 Dense | 实现多种策略用于调试和比较；本次固定数据集上 Dense 指标最高 |
| 按模型 Token 精确切块 | 同时限制字符数和估算 Token 数；估算值用于控制块大小，不等同于模型真实 tokenizer |
| Agent 会执行 Skill 包里的程序 | Skill 提供分析步骤；Agent 通过受控平台工具执行日志查询，ZIP 中脚本和二进制仍只供开发者终端使用 |

### 依赖部署条件，代码本身不能单独证明

| 能力 | 成立条件 |
|---|---|
| Kafka 后台整理历史 | Kafka 监听开关已开启，Topic、消费者组和重试配置可用 |
| Grafana/Loki 日志查询 | Loki 已收集应用结构化日志，Grafana Token 具备只读权限，时间范围和返回量限制生效 |
| Dense、Sparse、Rerank 检索 | Qdrant、Embedding、Sparse 编码器和 Rerank 服务均可用；降级发生时结果必须明确记录实际策略 |
| 文档后台入库 | MySQL、MinIO、Kafka、Docling 和 Qdrant 的部署版本与应用配置匹配 |
| 指标可复现 | 使用相同数据集、代码版本、模型版本、检索配置和随机种子重新运行评测 |

## 最终浓缩的六条主链路

这六条是面试时建议讲述的粒度。每条都从用户动作开始，讲到系统如何结束；专业术语只在需要对应源码时放在括号里。

## 主链路一：启动工作流，并确定下一个 Agent

### 这条链路解决什么问题

传统画布只能沿固定连线往下执行，Agent 很难根据当前对话主动选择下一条路。这条链路让 Agent 可以提交下一步建议，但最终选择权仍在服务端，避免模型跳到画布之外的节点。

### 文字链路

```text
用户在聊天页启动已经发布的智能工作流
-> 接口检查租户、用户、会话和工作流版本，并锁住当前会话的写入入口
-> 服务端记录本次使用的 runId、Trace ID、发布版本、配置摘要、起始节点和预算，并把已经编译好的执行计划交给当前后台任务
-> 数据库事务成功后，把真正执行工作流的任务交给后台线程
-> 后台线程从起始节点开始；每个节点开始前检查运行是否已取消，以及该节点的执行次数是否超限
-> 如果当前是 Agent 节点，就装配该节点的模型、提示词、知识库和工具配置并调用 Agent
-> 如果 Agent 因网络、超时、限流等暂时性问题失败，默认最多尝试 3 次，前两次分别等待约 500 毫秒和 1 秒
-> Agent 可以调用路由工具，提交一个“下一步想走哪条业务路径”的建议
-> 路由工具只保存建议，不直接修改当前节点，也不直接启动下一个 Agent
-> 当前 Agent 完成后，服务端读取这个建议，并与当前节点真实存在且已经启用的连线逐项比对
-> Agent 返回后汇总本次运行的实际 Token 用量和已经完成的节点数；达到上限时不再进入下一个节点
-> 建议合法就选择对应连线；没有提交建议时，系统只追加一次专门的选择请求，仍未提交才走默认出口或明确失败
-> 服务端保存本次路径选择和节点执行结果，再把 currentNodeId 更新为目标节点
-> 循环执行下一个 Agent，直到到达 END、用户取消、预算耗尽或发生无法继续处理的错误
-> 服务端写入最终状态和结束事件；前端通过 SSE 持续接收节点开始、节点结束、路径选择和运行结束消息
-> 用户重新连接时，可以从上次收到的事件序号继续获取遗漏消息，不会重新启动工作流
```

### 失败与重复请求

- 同一个启动请求携带相同的重复请求标识时，服务端返回原来的运行，不再创建第二个运行。
- Agent 没有调用路由工具时，系统只追加一次专门的选择请求，不会反复调用；仍没有合法建议时才按默认出口继续，没有默认出口则明确失败。
- 用户取消后，后台线程在进入节点、调用模型、等待重试和保存路径前都会再次检查，避免取消后继续执行新的 Agent。
- 参数错误、权限错误和重复调用等确定性问题不会重试；网络、超时、服务暂时不可用和限流等问题才会再次尝试。
- 如果重试次数用完，服务端只会选择当前节点配置的失败出口；失败出口直接到 `END` 时，整次运行保持失败状态。
- 后台线程池无法接收任务时，系统立即结束本次运行并写入失败事件，不会让运行一直显示“执行中”。

### 完成标志

智能工作流状态进入 `COMPLETED`、`FAILED` 或 `CANCELLED`，同时写入带连续序号的结束事件；预算耗尽会记录明确错误码并进入 `FAILED`。SSE 收到结束事件后关闭本次观看连接，但连接关闭不会反过来中断后台运行。

## 主链路二：Agent 每轮发现工具，并通过统一入口调用

### 这条链路解决什么问题

Agent 的可用工具会随用户权限、节点配置和工具发布状态变化，不能在创建 Agent 时永久写死。系统需要每轮重新生成工具清单，同时把不同来源的工具放到同一套权限、调用和记录流程中。

### 文字链路

```text
Agent 准备向模型发起新一轮请求
-> GatewayToolset 根据当前租户、用户、Agent、工作流节点和本次运行重新查询可用工具
-> 平台过滤未发布、已禁用、无权限或不属于当前节点的工具
-> 把结果转换成模型能理解的工具名称、用途和参数说明
-> 模型根据用户问题和当前中间结果决定是否调用工具
-> 不论选择的是 MCP、Skill 还是平台内置工具，都先进入 GatewayAdkTool
-> GatewayAdkTool 补齐可信的租户、用户、runId、Trace ID、节点和调用编号，再交给 ToolGateway
-> ToolGateway 再次检查当前运行是否还能继续、Trace ID 是否与数据库运行一致、工具是否属于当前节点，以及同一次函数调用是否已经执行
-> MCP 工具由统一 MCP 客户端转发；平台工具调用受控的 Java 处理器；Skill 读取已发布版本的 SKILL.md 说明
-> 成功领取执行权后创建数据库工具调用记录，正常情况下在结束时更新为成功或失败，并保存耗时、输入摘要和输出摘要
-> 工具结果返回 Agent，Agent 可以结合结果继续思考、再次调用工具或生成最终回答
```

### 关键边界

- 动态发现发生在每次模型请求前，不是只在 Agent 首次创建时执行一次。
- Skill 当前只把说明交给模型，不执行 ZIP 内脚本；需要真正运行的能力必须通过平台工具或 MCP 暴露。
- 普通 DAG 和智能工作流都会把当前节点配置的 MCP、Skill 清单带入运行上下文；工具清单生成和真正执行前都会再次核对。
- 稳定的 `runId + functionCallId` 用于识别重复工具调用；缺少这些字段时当前会退化为随机编号，这种情况下不能保证跨请求去重。

### 完成标志

成功领取执行权的工具调用会创建与运行、节点和 Trace ID 对应的数据库记录，并在正常收尾时更新为成功或失败；领取执行权前被拒绝的调用不会制造一条“已经开始”的记录。Agent 收到结果后进入下一轮模型请求或结束回答。

## 主链路三：Agent 主动检索知识库，并控制次数、成本和引用来源

### 这条链路解决什么问题

一次固定检索可能无法回答复杂问题。把 RAG 做成 Agent 可以主动调用的平台工具后，Agent 能根据第一次结果调整问题继续查找，同时由服务端控制总调用次数和返回文本量。

### 文字链路

```text
Agent 在动态工具清单中看到 rag_retrieve
-> 模型判断当前问题需要知识库内容，并提交检索问题和期望的最大上下文 Token
-> 平台从可信运行上下文取得租户、Agent、工作流绑定、runId 和 Trace ID，不接受模型伪造这些字段
-> 服务端检查问题长度、单次返回上限、本次运行已调用次数和累计 Token 预算
-> 超过默认 3 次调用或累计 8000 Token 时直接拒绝，不再访问向量库
-> 预算允许时，根据工作流绑定找到当前可用知识库和已启用文档版本
-> 按配置执行 Dense、Sparse 或两路混合搜索；RRF 用固定规则合并两路排名，启用 Rerank 时再调整前排候选
-> 外部向量结果返回后，服务端回 MySQL 核对租户、知识库、文档版本和当前生效的索引批次，过期或越权候选被丢弃
-> 对有效小块补充所属父块和相邻块，并按原文顺序去重、合并
-> 按本次剩余 Token 预算裁剪上下文，为每段生成稳定引用编号
-> 保存检索审计、候选变化、耗时、降级原因、预算消耗和引用来源
-> 将带引用编号的知识片段返回 Agent
-> Agent 可以根据中间结果改写自己的检索问题，再次调用 rag_retrieve，形成多次逐步查找
-> Agent 最终回答中使用引用编号；系统核对引用是否来自本次运行已经返回的证据
```

### 关键边界

- “多跳检索”不是服务端固定循环，而是 Agent 读完一次结果后主动调整问题，再次调用同一个工具。
- 当前预算和证据记录保存在单个 Java 进程内，可以控制一次正常运行，但多实例切换或进程重启后无法保证连续累计。
- 非法引用目前只写入消息附带的引用检查信息供排查，不会阻止答案保存，也不会自动要求模型重写。
- `queryRewriteEnabled` 目前没有对应的问题改写器；可描述为“Agent 根据结果调整问题”，不能写成“平台自动改写查询”。

### 完成标志

检索工具返回经过权限核对、上下文补充和 Token 裁剪的知识片段，同时生成检索记录和引用记录；最终回答保存后，可以从引用编号追溯到本次实际返回的文档块。

## 主链路四：保存近期对话，并整理较早历史

### 这条链路解决什么问题

长会话不能把全部历史原样塞进每次模型请求。系统把最近消息作为短期记忆，把较早内容整理成长期摘要，在尽量保留上下文的同时控制输入长度。

### 文字链路

```text
用户或 Agent 产生一条新消息
-> 服务端让同一会话的消息按顺序写入：读取当前最大消息序号并加一，避免并发消息使用同一个序号
-> 完整消息先保存到 MySQL，作为最终可信历史
-> 同一条消息按 sequenceNo 写入 Redis ZSet，保存最近一段对话并设置过期时间
-> 组装下一次模型上下文时，先读取长期摘要，再读取摘要之后的近期消息
-> Redis 中的消息序号完整连续时直接使用；缺少开头、结尾或中间任何一条时，从 MySQL 重新读取所需的完整区间
-> 按消息顺序估算 Token，并保留距离当前问题最近的内容
-> 如果模型已经决定调用工具，而上下文在工具执行前超过阈值，先同步整理较早历史，再带着新摘要继续执行工具
-> 一轮助手回答保存后，检查较早历史是否超过后台整理阈值
-> 超过阈值就创建有唯一标识的摘要任务并通知 Kafka，接口不等待摘要模型完成
-> Kafka 消费者回查 MySQL 中的任务记录，并用条件更新确保只有一个消费者开始处理，然后读取旧摘要和待整理消息
-> 摘要模型生成新的结构化摘要，服务端只在摘要版本没有被其他任务推进时更新
-> 摘要成功后删除 Redis 中已经被摘要覆盖的旧消息，保留最近尾部供下一轮直接使用
-> 失败任务按配置再次尝试；同一个任务被重复通知时，MySQL 中的任务状态保证只有一个消费者真正处理
```

### 关键边界

- MySQL 是完整历史，Redis 只是加速近期消息读取；不能因为缓存存在就假设它一定包含摘要后的全部消息。
- 同步整理只在工具真正执行前发生，不是每次模型调用前都会执行。
- Kafka 监听在当前开发配置中默认关闭；只有部署时开启消费者，这条后台链路才实际运行。
- Redis 中的消息必须从摘要后的第一条连续覆盖到本次需要的最后一条；前半段被裁掉、结尾不足或中间缺号都会回查 MySQL。
- Kafka 发布端会等待发送确认；通知失败不会影响已经保存成功的回答，数据库任务仍会被定时扫描再次通知。

### 完成标志

新的长期摘要以更高版本保存，记录自己已经覆盖到哪个消息序号；下一次上下文由这份摘要和其后的近期消息组成，不再重复放入已经整理过的原始历史。

## 主链路五：用同一个 Trace ID 关联请求、后台任务和日志查询

### 这条链路解决什么问题

一次 Agent 运行会跨过 HTTP、后台线程、工具、RAG、Kafka 和外部服务。统一的 Trace ID 可以把这些分散记录串成同一次业务运行，方便从失败结果反查具体阶段。

### 文字链路

```text
HTTP 请求进入 TraceIdFilter
-> 请求头带有合法 X-Trace-Id 就继续使用；没有则生成新的 Trace ID
-> Trace ID 写入当前线程上下文和日志字段，并随接口响应返回前端
-> 创建 Run、消息、节点执行、工具调用、RAG 审计和工作流事件时，把同一个 Trace ID 一起保存
-> 工作流转到线程池执行前，显式复制 Trace ID 和租户身份
-> 后台线程开始时恢复这些信息，结束时清理，避免线程复用后串到下一位用户
-> 发送 Kafka 任务时把 Trace ID 放入消息和 MySQL 任务记录
-> Kafka 消费者处理前恢复 Trace ID，完成或失败后清理线程上下文
-> 应用结构化日志被采集到 Loki，并可以在 Grafana 中按 Trace ID 精确筛选
-> Agent 查询分支：
-> Agent 在工具清单中看到 query_trace_logs 后，只能查询当前这次运行自己的 Trace ID
-> 服务端限制查询时间最多 120 分钟、返回最多 500 行，并固定生成 Grafana 查询，Agent 不能提交任意 LogQL
-> 平台工具通过 Grafana 的只读数据源接口读取日志，删除常见密码、令牌和密钥后按时间排序返回
-> Agent 根据平台工具返回的日志，查找最早失败、超时、取消、降级或缺少结束记录的位置，并结合日志证据解释原因
-> 开发者查询分支：
-> Cobra CLI 接收 Trace ID、运行编号、会话编号或检索编号，生成受限制的 LogQL 查询并调用 Grafana API
-> CLI 对结果分页、去重和按时间排序，再输出时间线、表格、JSONL 或原始日志
-> 如果精确时间窗口没有结果，按受控范围逐步扩大查询时间；失败时最多重试 3 次
-> 分析逻辑根据开始、结束、失败、降级、取消、慢阶段和候选数量变化，还原本次运行经历了什么
```

### 关键边界

- 这是项目内部统一传递的业务 Trace ID，不是 OpenTelemetry Span，也不能证明每个外部服务内部都有完整链路。
- 异步日志输出配置为业务线程不等待磁盘写入；日志系统繁忙时可能丢少量日志，因此数据库审计记录仍是关键事实来源。
- Agent 不执行 Skill ZIP 里的二进制，也不能运行任意 Shell；Agent 使用受控平台工具，开发者在终端中使用 Cobra CLI。
- `query_trace_logs` 默认关闭，部署时必须提供只读 Grafana 账号并显式开启；没有正确采集到 Loki 的日志仍无法被查询。

### 完成标志

开发者可以通过 CLI 和配套 Skill 查询受控业务编号；Agent 只能通过平台工具读取当前运行的脱敏日志并定位失败或慢阶段。数据库记录与日志结果可以相互核对，但不能把日志缺失当成“某一步一定没有执行”。

## 主链路六：解析 PDF/DOCX，建立父子块并评测检索效果

### 这条链路解决什么问题

文档入库不能只把整篇文本按固定长度切开，否则标题、表格和章节上下文容易丢失。系统先把不同格式转换成统一文档结构，再按结构切块、建立索引并用固定问题集验证检索位置。

### 文字链路

```text
用户上传 PDF、DOCX 或 Markdown 文件
-> 接口校验租户、文件类型、大小和文件名，把原文件保存到 MinIO，并根据文件内容哈希识别同一知识库中的重复上传
-> 在 MySQL 创建文档版本、入库任务和待发送事件；数据库事务成功后再通知 Kafka
-> Worker 收到通知后回查 MySQL，并用带超时时间的条件更新领取任务，防止多个实例同时处理同一版本
-> PDF 交给 Docling 解析；DOCX 优先使用 Apache POI，本地解析失败时再交给 Docling；Markdown 使用 CommonMark AST
-> 不同解析器都输出统一文档结构（Document IR），保存标题层级、段落、表格、代码、公式、图片和阅读顺序
-> PDF 额外保存页码和版面位置；DOCX 没有固定渲染器时明确记录页码不可用
-> 服务端保存解析原结果、Document IR、标准化 Markdown 和质量报告到 MinIO
-> 切块器沿标题和内容结构生成父块与小块，表格跨块时重复表头，代码、公式和图片不与普通段落混切
-> 小块保留 parentChunkId、前后相邻关系、章节路径和页码范围
-> 展示正文保持原文；用于向量化的文本额外加入文档标题和章节路径
-> 小块分批生成 Dense 和 Sparse 向量并写入 Qdrant，每批成功后把进度写回 MySQL
-> 全部写入后，核对 Qdrant 向量数量、MySQL 小块数量和 MinIO 主产物的大小与 SHA-256
-> 核对通过后，在一个事务中启用新文档版本和新的索引批次；失败时旧版本继续提供查询
-> 检索命中小块后，再补充父块和相邻块，按原文顺序组成完整上下文
-> Benchmark 使用固定的 200 个问题分别执行 Dense、Sparse、Hybrid RRF 和 RRF + Rerank
-> 保存每次返回排名、耗时、候选变化和降级信息，再与标准相关文档列表计算 Recall、MRR、nDCG 和 MAP
```

### 失败与后台继续

- Kafka 只负责提醒 Worker 有任务，任务真实状态保存在 MySQL；即使通知丢失，定时扫描仍能找到未完成的入库任务。
- Worker 每个阶段保存进度并延长自己的处理时限；进程重启或处理超时后，其他 Worker 可以从数据库已经确认的阶段继续。
- Docling 遇到网络错误或 5xx 会立即再请求一次；完整请求超时、4xx 和非法响应不在适配器内重复请求，之后由 Worker 判断是稍后整体重试还是直接失败。
- 暂时性错误最多尝试 3 次，等待时间从 5 秒逐步增加、最长 5 分钟；取消或最终失败只清理目标版本，新版本未启用前不影响旧版本检索。

### 指标结论和边界

- 当前 Dense 在成对 SciFact 数据集上：PDF 的 Recall@1/5/10 为 82.5%/93.5%/96%，nDCG@10 为 0.8975；DOCX 为 83.5%/95%/96%，nDCG@10 为 0.9040。
- 两种格式各使用 200 个问题，四种策略各执行 200 次；运行结果为 0 错误、0 降级、0 空结果。
- 指标衡量相关文档是否被找到以及排位，不衡量最终回答是否正确。
- 这次实验中 Hybrid/Rerank 没有超过 Dense，因此它们的价值应表述为提供调试和策略比较能力，而不是保证提升效果。

### 完成标志

新版本的解析产物、分块和向量全部通过数量与摘要校验，并在同一事务中进入可检索状态；评测只有在每种策略都完成 200 个问题且结果文件通过完整性检查后才计算指标。
