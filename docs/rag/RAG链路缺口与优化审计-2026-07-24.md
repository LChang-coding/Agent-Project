# RAG 链路缺口与优化审计（2026-07-24）

## 1. 审计边界

本文回答的不是“RAG 能不能跑”，而是“现有链路在哪些条件下仍可能给出错误、缺失或难以解释的结果”。结论只来自当前代码、项目内测试产物和已经固化的真实运行证据；没有原始证据的项目统一标为“待测”，不估算数据。

当前生产链路为：

`MinIO 原件 → Outbox/Kafka 唤醒 → Worker 租约 → Docling/Markdown 解析 → 结构化 Parent/Child 切块 → Dense/Sparse 向量 → Qdrant → Dense/Sparse 召回 → RRF → Rerank → Token 预算组装 → 模型回答 → 引用校验`

主要证据：

- 当前实现：`DoclingDocumentParserAdapter`、`StructuredRagChunker`、`RagIngestWorker`、`RagRetrievalService`、`ContextInjectionPlugin`、`RagAnswerCitationValidator`。
- 完整质量结论：[RAG完整测试数据与瓶颈分析](evaluation-results/final-report/RAG完整测试数据与瓶颈分析.md)。
- 失败案例：[SciFact 失败案例](evaluation-results/scifact-r11-failure-cases.md)。
- 三格式真实链路：[format-e2e-r6](evaluation-results/format-e2e-r6/summary.json) 和 [页码证据](evaluation-results/format-e2e-page-r4/summary.json)。

## 2. 已确认的能力与边界

| 项目 | 已确认事实 | 不能外推的结论 |
|---|---|---|
| 三格式摄取 | Markdown、DOCX、PDF 均完成真实 MinIO→Worker→Qdrant→检索；r6 为 15/15 有答案问题通过 | 每种格式只有一份小型受控文档，不能代表复杂合同、扫描件、超大表格 |
| 检索质量 | SciFact 300 问题×4 变体共 1200 条，0 error、0 degraded、0 empty，并经独立复分 | SciFact 没有 gold answer，不能证明回答 Faithfulness 或 Answer Correctness |
| Dense | Recall@10 0.797944、MRR@10 0.655835、nDCG@10 0.683385 | 只代表冻结模型、语料和参数 |
| Sparse | Recall@10 0.487778、MRR@10 0.321922、nDCG@10 0.355442 | 不能说明 Sparse 没价值；它对专有名词、编号型问题仍可能提供互补召回 |
| Hybrid RRF | Recall@10 0.750667、MRR@10 0.566630、nDCG@10 0.604539 | 当前混合配置低于 Dense，不能宣传“混合一定更好” |
| Hybrid+Rerank | Recall@10 0.750667、MRR@10 0.646028、nDCG@10 0.663244 | Rerank 只改善混合结果排序；并未恢复 RRF 前已丢失的文档 |
| 容量 | 并发 1/2 健康；并发 4 出现 67.19 秒和 `rerank_fallback` | 不能宣称并发 4 SLA；首瓶颈已证实为 Reranker CPU、排队和子批放大 |

## 3. 分阶段缺口、原因与优化方案

### 3.1 上传、原件与任务创建

**当前设计**

- 文件先进入 MinIO，数据库保存文档、版本、任务和 Outbox；Worker 使用租约、重试、检查点与幂等状态推进。
- 文件格式、大小、文件名和受控临时目录有边界校验。

**考虑不足**

- 文件扩展名、MIME 与实际 magic bytes 的一致性没有形成独立安全门禁证据。
- 未证明密码保护 PDF/DOCX、损坏压缩包、超大页数、压缩炸弹、重复上传和同内容异名文件的行为。
- 当前取消能阻止后续阶段，但已经发出的远程 Docling/Embedding/Rerank HTTP 请求无法真正撤回。

**优化**

1. 上传后增加 magic bytes、ZIP 目录规模、加密状态和页数预检；拒绝伪装格式与异常膨胀比。
2. 以租户+内容 SHA-256 建立可配置去重策略，区分“复用已有版本”和“强制新版本”。
3. 为远程模型请求增加任务取消令牌；无法撤回时至少丢弃迟到结果，并记录 `cancelled_after_remote_dispatch`。

**验收**

- 建立损坏、加密、伪 MIME、重复内容、50MiB 边界和取消竞态用例；核对 MinIO、MySQL、Qdrant 无孤儿数据。

### 3.2 文本解析与结构保真

**当前设计**

- Markdown 使用 Java 有界 UTF-8 读取；PDF/DOCX 交由 Docling，同时请求 Markdown 与 JSON。
- 已保留 heading、页码及解析器版本；固定页 PDF 的章节页码已在真实 E2E 中与金标一致。

**具体不足**

1. **表格不够细**：切块器只把 Markdown 表格识别为原子块；没有表头继承、跨页表格拼接、合并单元格、行列坐标和单元格级引用。宽表超过预算时仍会按字符切开，问题可能只命中数值而丢失表头。
2. **扫描件/OCR 不够细**：虽然命令支持 `ocrEnabled`，但没有按页 OCR 置信度、语言、旋转角度、版面阅读顺序和低置信度告警的闭环评测。
3. **页眉页脚不够细**：没有已证明的重复页眉、页脚、页码、水印去噪；它们可能在多个块中放大词频，污染 Sparse 与 Dense。
4. **图像和公式缺失**：当前明确 `include_images=false`、`include_page_images=false`；图表、流程图、截图、公式语义不会进入检索文本。
5. **DOCX 页码语义有限**：流式文档的页码依赖排版引擎，项目当前只对 PDF 给出页码金标；DOCX/Markdown 不应猜页码。
6. **Markdown 语法覆盖有限**：只明确处理标题、列表、围栏代码和管道表格；HTML 表格、脚注、定义列表、引用嵌套、任务列表和复杂代码围栏待测。

**优化**

- 将 Docling JSON 中的 block 类型、bbox、页码、阅读顺序和表格结构持久化为规范化 block，而不是先压平成 Markdown 再重新猜结构。
- 表格采用“表摘要父块 + 表头重复的行组子块 + 单元格坐标元数据”；跨页表以表头和几何位置判定续表。
- 建立版面去噪器：跨页高重复+固定位置文本只保留文档级元数据，不参与正文向量。
- OCR 增加逐页置信度、语言检测、旋转纠正和人工复核阈值；低置信度文档进入 `ready_with_warning`，而不是静默 READY。
- 对图像/公式增加可选的视觉描述通道；资源紧张时只对含图页、低文本密度页按需执行。

**验收**

- 新增跨页表、合并单元格、双栏、页眉页脚、扫描旋转、多语言、公式和截图金标集；指标至少包括字符召回率、章节顺序正确率、表格单元格 F1、页码正确率和 OCR CER。

### 3.3 Parent/Child 切块

**当前设计**

- `StructuredRagChunker` 优先按 heading、段落、列表、代码和表格边界切分；支持 Parent/Child、字符/估算 Token 双预算、重叠和稳定哈希。

**考虑不足**

- Tokenizer 是 `approx-unicode-v1`，与真实 Embedding/LLM tokenizer 不同；中英文、代码和长数字的误差可能导致块超限或预算浪费。
- 超大表格/代码最终仍按字符切分，不理解行、函数或语句边界。
- overlap 是固定字符数，可能重复无价值文字，也可能没覆盖代词、定义或跨段条件。
- Parent 只按同 heading 和预算聚合，没有语义断点、跨章节引用、邻块图或文档级摘要。
- 当前评测没有独立隔离“父块、邻块、chunk 大小、overlap”对质量的真实增益。

**优化**

1. 使用与 Embedding/生成模型一致的 tokenizer，并把实际 token 数持久化。
2. 采用两阶段切块：先保结构原子，再用句向量/主题突变做语义边界；表格和代码使用专用切分器。
3. 保存 `previous/next/parent/section-summary` 图关系；首轮命中子块后按预算动态扩展邻块，而不是固定 overlap。
4. 对标题过短、正文过长、引用跨节等异常生成质量告警。

**验收**

- 固定同一文档、模型和查询，对 chunk 大小、overlap、parent、neighbor 做配对消融；报告 Recall@K、MRR、上下文冗余率、平均 Token 和延迟。

### 3.4 Embedding 与 Sparse 编码

**当前设计**

- Query/Document 输入类型分离，向量维度受知识库配置约束；Embedding 有批次、并发、重试和响应校验。
- Sparse 使用确定性词表版本，能够复现。

**考虑不足**

- 没有跨版本向量漂移门禁；模型或 tokenizer 升级后，旧向量与新 query 向量混用可能静默降质。
- 没有领域词、缩写、中文切词、拼写错误和编号的专项 Sparse 评测。
- 确定性 Sparse 不等于学习型稀疏模型；当前质量低于 Dense 已被证明，但原因不能只归咎于“词法检索差”。

**优化**

- 索引 payload 固化 embedding model、revision、dimension、normalization、tokenizer 与 sparse vocabulary；查询时严格匹配。
- 模型升级采用新 generation 双写/影子查询，质量门禁通过后原子切换。
- 中文/专有名词场景评估 BM25、学习型 Sparse 或领域词典，并加入 query 拼写归一、缩写扩展。

**验收**

- 构建模型升级兼容测试和词项型专项集；不允许跨 revision 检索，升级前后做配对质量与资源对比。

### 3.5 Qdrant 索引与生命周期

**当前设计**

- generation 隔离新旧版本，成功后切 active generation；删除、重建和租户/知识库/文档过滤有显式范围。

**考虑不足**

- 未看到线上规模下 HNSW 参数、量化、payload 索引、segment 优化和磁盘水位的系统容量曲线。
- Worker 失败、数据库提交成功但向量提交状态不一致时，虽有幂等恢复，仍需要周期性三端对账。
- 目前三格式只验证小规模点数一致，不能代表百万块级重建窗口。

**优化**

- 增加定时一致性审计：MySQL active child 数、Qdrant generation 点数、MinIO 版本对象三方核对。
- 用真实分布压测 HNSW `m/ef_construct/ef_search`、量化和 payload index，按召回损失与资源收益选型。
- 重建采用新 collection/generation、校验、原子切换、延迟清理；磁盘不足时提前拒绝，不在中途失败。

### 3.6 查询理解与多路召回

**当前设计**

- 支持 Dense、Sparse、Hybrid；按绑定读取 profile，最多 32 个绑定；必选绑定失败则失败，可选绑定允许显式降级。

**明确缺口**

- `queryRewriteEnabled` 当前只产生 `query_rewrite_unavailable:<profile>` 降级标记，没有真正的查询改写。
- 没有多轮对话中的指代消解、时间/实体/权限过滤抽取、HyDE、多查询扩展或问题路由。
- 无答案问题仍可能返回 5～6 个候选；“有候选”不等于“有答案”。

**优化**

1. 查询改写必须保留原问题、改写问题、触发原因和耗时；低置信度时同时召回原查询，避免改写漂移。
2. 将多轮历史压缩成独立检索查询，禁止把整段聊天直接向量化。
3. 增加 query classifier：事实查找、编号/精确词、摘要、多跳、表格、无答案；按类型选择召回策略。
4. 加入绝对分数/相对间隔/跨路一致性和证据覆盖的拒答门控。

**验收**

- 指代、省略、缩写、拼写错误、多跳和无答案专项集；分别报告改写前后 Recall、错误改写率、拒答准确率和额外延迟。

### 3.7 RRF 融合、去重与 Rerank

**当前设计**

- Qdrant/服务层支持 Dense/Sparse 合并、RRF、内容哈希去重和 Cross-Encoder Rerank；内部诊断可以记录各阶段排名。

**已证实问题**

- 当前 Hybrid 的四项总体指标均低于 Dense，说明固定权重/候选规模没有适配本数据集。
- Rerank 对 Hybrid 的 MRR@10、nDCG@10、MAP@10 分别提升约 0.079398、0.058705、0.075396，但不改变 Recall@10；它无法救回融合前丢失的 Gold。
- Rerank 一次 Top10 被拆成多个远程子批，并发 4 时 CPU/排队触发 60 秒 deadline；取消也无法撤回已经发出的子批。

**优化优先级**

1. **P0：Rerank 批处理与排队**。按服务 permit、batch token 和候选长度动态组批；增加队列预算，超预算直接跳过并记录原因。
2. **P0：融合校准**。用验证集搜索 Dense/Sparse 权重、RRF k、各路 TopK；按 query 类型动态选择 Dense-only、Sparse-only 或 Hybrid。
3. **P1：去重升级**。内容哈希只能去完全重复；加入相似块聚类、同文档多样性和 MMR，避免 TopK 被近重复块占满。
4. **P1：两级重排**。先用便宜特征筛到较小集合，再调用 Cross-Encoder；缓存 query+chunk revision 得分。

**验收**

- 每个参数/组件使用同一 query 的配对消融，单独报告质量、Rerank 调用率、队列等待、批次数、CPU、p95、降级率；并发 4 必须 0 fallback 才可提升容量声明。

### 3.8 上下文预算与回答

**当前设计**

- Context Manager 在会话记忆与 RAG 证据之间做预算分配；引用按完整 citation 组装，不截断半条证据。
- 本次新增会话级 RAG 开关，设置持久化到 `chat_session.rag_enabled`，运行创建时快照到 `chat_run.rag_enabled`；一次运行中不会因用户中途切换而改变语义。

**考虑不足**

- 预算估算仍可能与实际模型 tokenizer 有偏差。
- 证据选择主要依赖排序和长度，没有明确的“问题子事实覆盖率”、跨文档多样性和冲突证据策略。
- 没有证明最终 LLM 对无答案、冲突答案、恶意文档提示注入的稳定行为。
- 开关打开但 Agent/Workflow 未绑定知识库时只给 UI/接口告警，用户仍可以发送消息；这是有意的非阻断策略，需要产品确认。

**优化**

- 使用实际模型 tokenizer；在发送前记录预算、实际 prompt tokens 和误差。
- Context packing 使用边际信息增益：覆盖新实体/子问题的证据优先，近重复和低增益块后置。
- 文档内容与系统指令严格分隔，对“忽略之前指令”等提示注入做检测、转义和审计。
- 增加回答前证据充分性判断：不足则拒答或追问，不要求模型硬答。

### 3.9 引用与可验证性

**当前设计**

- 只接受本次实际注入的 citation ID；伪造、跨检索、重复映射和非法引用会被 `RagAnswerCitationValidator` 拒绝。
- 引用可解析回文档、版本、章节和页码。

**考虑不足**

- 当前验证的是“引用 ID 是否允许”，不是“引用内容是否蕴含回答中的具体断言”。
- SciFact 没有 gold answer，因此现有 1200 条不能填充 Faithfulness、Answer Correctness 或 Citation Entailment。
- 多断言回答可能只挂一个引用，缺少 claim→citation 的覆盖率。

**优化与验收**

- 将回答拆成原子 claim，对每个 claim 做引用覆盖与 NLI/LLM judge 蕴含判断；judge 必须有人工抽样校准。
- 新建有 gold answer 与 gold citation 的内部集，报告 Faithfulness、Answer Correctness、Citation Precision/Recall 和拒答准确率。

### 3.10 权限、可观测性和故障恢复

**当前设计**

- tenant/user/session/run 身份来自可信运行时；检索、引用回查、绑定与知识库状态均有范围校验。
- 本次将 `traceId` 作为整条链路唯一检索键，贯通 HTTP、会话、run、Context、RAG、模型、工具、Outbox/Kafka 和 Worker；`traceId` 只作为 logfmt 字段，不作为 Loki label，避免高基数。
- 每条结构化业务日志自动带稳定 `event`、中文 `eventName`、中文 `message`，并带 `runId/retrievalId/taskId/stage` 等局部键；Grafana 可按一个 TraceId 升序还原完整链路。

**仍需注意**

- Kafka 消费依赖 Outbox 中持久化的 trace；历史 trace 为空的旧任务无法逆向恢复。
- 第三方服务日志不一定带本系统 trace；只能通过本端远程调用节点、任务 ID 和时间窗关联。
- 不应把 traceId 做 Loki label；生产中需要用时间范围+字段过滤，并设置合理保留期。
- 日志禁止记录原始问题、文档正文、Token、API Key、密码和附件内容；当前 RAG 开始日志只记录 query 长度。

**验收**

- 以一个新会话和一份新文档分别跑摄取、RAG 开/关聊天、模型和工具路径；从响应头取得 TraceId，在 Grafana/Loki 中断言节点顺序、中文可读、无敏感正文，并能定位同一 run/retrieval/task。

## 4. 优先级路线

| 优先级 | 工作 | 原因 |
|---|---|---|
| P0 | Rerank 动态批处理、队列预算、并发 4 零降级复测 | 已有真实容量失败，直接影响稳定性 |
| P0 | 真实 tokenizer + Token 误差闭环 | 同时影响切块、上下文预算和模型成本 |
| P0 | 融合参数校准与 query 路由 | 当前 Hybrid 实测低于 Dense |
| P0 | 无答案/证据不足拒答门控 | 当前“返回候选”不能证明“有答案” |
| P1 | Docling block/bbox/table 结构直存 | 解决表格、跨页、阅读顺序与精确引用 |
| P1 | 页眉页脚去噪、OCR 质量告警 | 降低重复污染和静默低质量 READY |
| P1 | claim→citation 蕴含验证 | 补齐生成端正确性，而非只验 citation ID |
| P1 | Parent/neighbor/语义切块真实消融 | 当前实现完整，但增益尚未被隔离证明 |
| P2 | 视觉图表/公式通道 | 价值高但资源成本也高，先按需触发 |
| P2 | 百万块级重建与一致性巡检 | 小规模三端一致性已证明，规模边界待测 |

## 5. 下一轮不得省略的评测

1. 解析：复杂 PDF/DOCX/Markdown，每类至少覆盖表格、双栏、页眉页脚、扫描 OCR、公式/图片和损坏文件。
2. 切块：真实 tokenizer、chunk/overlap、Parent、neighbor、语义切块的同问题配对消融。
3. 检索：查询改写、query 路由、融合参数、MMR、Rerank 动态批次的质量与性能双指标。
4. 生成：有 gold answer 的 Faithfulness、Answer Correctness、Citation Precision/Recall、无答案拒答和提示注入。
5. 容量：闭环并发与 open-loop 到达率分开；同步采集 App、MySQL、Qdrant、Embedding、Reranker、Docling 的 CPU、内存、队列和网络。
6. 可靠性：每个阶段注入超时、429/5xx、进程重启、Kafka 重复、租约过期、取消和迟到响应，核对无污染、可恢复、可追踪。
