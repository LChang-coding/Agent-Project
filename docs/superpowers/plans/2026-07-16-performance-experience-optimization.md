# 低资源服务器性能与前端体验优化总计划

## 目标

在不上传本地项目、不破坏现有租户隔离和 Agent 运行语义的前提下，降低服务器中间件与后台任务的 CPU、内存、线程、连接、磁盘和网络消耗；同时优化 Web 端的加载性能、操作反馈、视觉层级、响应式布局与组件遮挡问题。

## 强制约束

- 遵循 `codex.md` 的模块边界、安全、注释、测试和中文提交规范。
- 仅在服务器上读取运行态指标或调整已部署中间件配置，不上传本地源码、构建产物或资料。
- 服务器配置变更前必须留存原配置和回滚路径；涉及重启、公网可用性或数据风险时单独列出。
- 不提交现有日志、`data-alloy/`、`docs/design-questions/`、`docs/design-viz-methodology.md` 和 `skills/` 等用户文件。
- 每个重大闭环先在本文档或子计划中明确操作，执行后追加证据、测试、风险和回滚方式，然后进行中文本地提交。

## 优化前基线指标

### 服务器与中间件

- 整机：CPU 核数与负载、内存/Swap、磁盘容量与 IO、进程/容器资源排名。
- MySQL：容器/进程资源、缓冲池、最大/当前连接、慢查询、临时表和主要业务表索引。
- Kafka：JVM 堆、Broker 线程、日志保留、Topic 分区/副本与积压。
- Nacos：JVM 堆、实例数、日志与心跳/配置频率。
- MinIO：进程内存、对象容量、未完成上传与日志。
- XXL-JOB：Admin 与执行器资源、扫描频率、线程池、失败/过期日志。
- Grafana/日志栈：容器资源、采集频率、保留周期和磁盘占用。

### 后端代码

- 定时任务、上下文压缩、会话读取、Token 统计、附件解析、工具调用和消息流式链路的执行频率与关键查询。
- 线程池、HTTP/数据库连接池、Kafka consumer、无界队列、轮询和重试策略。
- 慢 SQL、N+1、重复查询、全量加载、大对象复制、重复 Token 计算与不必要日志。

### Web 前端

- `npm run build` 的总体积、首屏主 chunk、大路由 chunk 和构建时间。
- API 请求数、重复加载、会话长列表渲染、组件更新和静态依赖。
- 桌面与窄屏下的遮挡、溢出、z-index、弹层定位和可操作性。
- 发送、取消、引导、上传、删除、分享、刷新等操作的 idle/loading/success/error/disabled 反馈完整性。

## 执行阶段

### 阶段 1：现状盘点与可量化基线

1. 读取 Git 工作区、工程结构、启动配置、Docker/部署资料和前端构建信息。
2. 通过 SSH 只读采集服务器资源、容器、端口、挂载、中间件启动参数和日志体量。
3. 列出 P0/P1/P2 优化候选，区分“可立即安全调整”和“需停机/有回滚要求”。

### 阶段 2：中间件与部署资源收敛

1. 按实际瓶颈调整 JVM 堆、容器限制、连接数、日志保留、采集/扫描频率和 Topic 保留。
2. 保留配置备份，逐个验证健康状态、公网访问和业务连通性。
3. 记录调整前后的资源差值与回滚命令，仅提交本地运维文档，不提交密钥。

### 阶段 3：后端耗时链路优化

1. 优先处理高频轮询、重复查询、无界并发、缺少分页/批处理和大文本反复组装。
2. 针对定时任务、压缩、Token、附件、会话和工具链路分别补充与优化点相关的测试。
3. 保持流式/非流式、取消/引导、上下文压缩与租户隔离语义不变。

### 阶段 4：前端性能与体验重构

1. 先建立统一操作状态表达：按钮内容、进度/加载、成功、错误、禁用原因和防重提交。
2. 重构会话工作台的布局和视觉层级，修复遮挡/溢出，建立统一 z-index 和响应式规则。
3. 对路由、重型依赖、列表渲染、请求去重和无效刷新做可测量优化。
4. 使用一致的“专业工作台/编辑台”方向：清晰密度、稳定视觉锚点、克制动效和高可读性，不为增加复杂度而增加装饰。

### 阶段 5：综合回归与对比文档

1. 执行相关 Java 单测/集成测试、前端类型检查与生产构建，可行时补关键路径 E2E。
2. 复采服务器与中间件指标，保持采样口径一致；无法严格对比的指标明确标注。
3. 输出完整的优化前后对比文档，覆盖指标、改动、收益、风险、回滚、测试和未完成项。

## 中间件变更门禁

- 只读调查可直接执行。
- 修改配置但不重启前：必须先备份、校验语法并写出回滚命令。
- 需要重启容器/服务、改变公网端口或可能中断实时会话时：在子计划中单独记录影响和验证窗口，再执行。
- 数据删除、表结构变更、Topic 分区/副本变更和对象清理不在默认授权内，需要额外证据与明确方案。

## 执行实录

### 阶段 1：现状盘点与可量化基线

- 已完成本地 Git/工程/配置/SQL/前端构建的只读审计，并用三个 Target 分别收口服务器中间件、后端耗时链路与前端性能/体验证据。
- 服务器审计全程只读：未改配置、未重启、未删除、未上传，也未绕过 MySQL 认证。
- 确认的服务器首要风险为：Kafka 1 GiB 堆等于 1 GiB 容器上限且只读 CLI 已 OOM；宿主无 Swap；多数容器无资源限制；70 GB 数据盘未挂载；Loki Docker 日志增长高于时序数据本身。
- 确认的后端首要热点为：流式取消按时间和每模型事件重复查数据库；工具前压缩 50ms 热轮询；Rx IO/commonPool/阻塞流混用；Context Insight 全量重复读取；MinIO Client 与桶检查不复用。
- 确认的前端首要问题为：长会话全量加载/渲染且流式每字符 O(N) 扫描；分享条破坏 Grid 行并裁切组合器；会话切换重复请求；Workflow 写操作并发/乱序；Skill/MCP 窄屏操作列被隐藏。
- 已建立 `docs/performance/2026-07-16-performance-baseline.md`，记录数值、证据、P0/P1/P2 候选和可量化验收口径。
- 基线构建：Vite 7.3.6 处理 1914 modules，构建约 843ms；JS 285.27 KiB、CSS 42.42 KiB，主 chunk 167.14 KiB / gzip 64.36 KiB。

阶段 1 结论：基线证据已足以进入实施。中间件改动需分为“在线低风险”与“需重启/迁移”两类；先落地不需远程停机的应用资源默认值、MinIO 连接复用、聚合查询和前端明确缺陷，同时为 Kafka/日志栈/数据盘单独编写变更与回滚计划。

### 阶段 2：中间件与部署资源收敛

- 服务器增加 2 GiB、swappiness=10 的应急 Swap；Kafka 堆从 1G/1G 收敛为 256m/512m。
- 为 Kafka、Nacos、MinIO、Loki、Grafana、XXL Admin/MySQL 固化 memory、PID 与 20m×3 日志上限，均保留服务器本地配置备份与回滚点。
- 七个中间件合计稳定内存约从 2848 MiB 降至 2036–2048 MiB，减少约 28%；最终健康码与容器 restart 门禁全部通过。
- 未迁移 70 GB 数据盘、未清理历史业务数据或镜像缓存、未上传本地项目。

### 阶段 3：后端耗时链路优化

- 收敛通用线程池、Hikari、日志队列与日志上限，复用 MinIO 客户端和桶就绪状态。
- Context Insight 改为聚合查询；压缩等待改为指数退避；运行状态增加短期快照；工作流改为有界双池并传播租户身份。
- 调度协调采用 dirty scan/hash/CAS，派发改为有限波次并发；附件正文、Skill ZIP 均建立数据库到领域的双层字节边界。
- 最终 full clean 验收发现并修复 MinIO 与运行控制服务的 Spring 多构造器装配问题，完整应用上下文测试通过。

### 阶段 4：前端性能与体验重构

- 会话流式更新、自动滚动、重复请求和操作状态完成收敛；控制台写操作具备行级防重、迟到响应隔离和成功/失败反馈。
- 建立统一语义 z-index、宽表 sticky 操作列和 320/390/768 响应式卡片，修复组件遮挡与组合器裁切。
- 长会话首次只取 50 条、按 cursor 分页并将 DOM 限制为 100 条，保持历史前插滚动锚点。
- 最终生产构建通过；主入口小幅下降，但新增功能使 dist 总量增长约 4.9%，未把未达体积目标包装为完成。

### 阶段 5：综合回归与对比文档

- Java 17 完整 reactor clean 共 138 项：124 通过、14 项测试夹具/配置错误、0 failure、0 skip；完整应用上下文与所有性能专项 clean 测试通过。
- 前端 `vue-tsc + Vite` 构建 1914 modules、857ms；服务器最终内存、Swap、磁盘、容器边界和健康状态已复采。
- 完整交付文档为 `docs/performance/2026-07-16-optimization-before-after.md`，明确记录收益、回滚、未达目标和未执行 E2E/数据迁移。
