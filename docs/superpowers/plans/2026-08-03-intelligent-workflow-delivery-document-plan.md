# 智能工作流交付文档编制计划

## 目标

将已确认的两项需求固化为可直接指导开发、测试和上线验收的交付文档：

1. 所有节点可参与智能路由，路由引擎统一裁决和调度。
2. 工作流所有中间节点输出通过结构化事件流式传输，前端在聊天回答上方按节点执行实例展示。

`traceId` 必须贯穿 HTTP、工作流运行、节点执行、模型、工具、RAG、异步消息、持久化事件和前端展示，作为上线硬门禁。

## 执行步骤

1. 阅读 `codex.md` 及现有 Trace/Workflow 计划，统一分层、命名、事件和测试约束。
2. 编写交付文档，覆盖范围、非目标、总体架构、前后端契约、Trace 不变量、持久化、兼容性和分阶段交付物。
3. 建立测试矩阵，覆盖单元、契约、集成、端到端、断线恢复、取消、并发、循环、权限、安全、性能、故障恢复和可观测性。
4. 将每类测试的输入、操作、断言、证据和通过标准写清，禁止只写“测试通过”。
5. 进行无上下文读者审查，检查文档是否存在歧义、矛盾、隐含前提或遗漏验收条件。
6. 将实际产出、读者审查结论和文档校验结果追加到本计划。
7. 仅提交本次新增文档，不提交日志、评测数据或工作树中的无关改动。

## 文档验收门禁

- 两项主需求都有明确的前端、后端、数据和运维交付物。
- 必须明确“Agent 只有路由建议权，路由引擎拥有裁决权，运行时拥有调度权”。
- 必须区分 `nodeId` 与 `nodeExecutionId`，循环不能覆盖历史输出。
- 流式事件必须可排序、可去重、可持久化、可断线续传。
- `traceId` 在每个边界都有生成、传播、恢复和验证规则，不允许异步断链。
- 测试矩阵必须包含成功、分支、循环、异常、取消、断线、重启、跨租户、高并发和 Trace 完整性。
- 所有通过结论都必须指向可复查证据。
