# AI Agent Scaffold 阶段能力规划与核心提示词

> 文档状态：需求规划稿（待代码调研后转技术设计）
> 编写日期：2026-07-14
> 本轮范围：只澄清需求、建立统一设计约束、拆分实施阶段并提供后续开发提示词；不基于现有代码作实现承诺。

## 1. 目标

本阶段需要补齐五类能力：

1. 上下文压缩增加“调用工具前”的检测与阻断机制；
2. 为正在执行的会话增加取消能力；
3. 为正在执行的会话增加引导（steer）能力；
4. 支持会话导出、分享和由其他用户导入；
5. 建立分布式定时任务模块，并补齐管理端前端。

这些功能不能彼此独立实现。上下文压缩、取消、引导和工具调用共同修改一次会话执行所依赖的有效上下文，因此必须先建立统一的运行状态、消息有效性和上下文版本模型，再实现具体按钮和接口。

本阶段的最终目标不是“界面上出现功能”，而是：

- 被取消或被替代的消息永远不再进入模型上下文、压缩结果或后续执行；
- 工具调用前存在最后一道可验证的安全门，避免取消后仍产生工具调用及额外消耗；
- 压缩任务在并发取消、引导和新消息时不会覆盖更新后的上下文；
- 分享内容可审计、可过期、可校验、可安全导入，不直接转移原会话所有权；
- 定时任务在多实例部署下不重复生成、不重复执行，Cron 修改后能稳定收敛。

## 2. 术语与统一对象

后续设计和代码应统一使用以下概念，避免用“当前消息”“当前任务”等模糊描述：

- `session`：用户看到的会话容器。
- `turn`：一次用户输入及其触发的完整处理周期。
- `run`：一次可被取消、引导、重试的执行实例。一个 turn 可以因引导或恢复产生多个 run。
- `message`：用户、助手、系统、工具请求、工具结果等消息记录。
- `context_revision`：会话有效上下文的单调递增版本。消息有效性、压缩快照激活、引导等改变有效上下文的动作都必须推进版本。
- `compaction_task`：基于特定上下文版本和消息集合生成摘要的异步任务。
- `context_snapshot`：压缩生成的上下文快照；生成成功不等于可以激活。
- `steer`：用户在 run 尚未结束时追加的方向修正指令。
- `schedule_definition`：定时任务配置来源及其当前版本。
- `schedule_task`：由配置物化出的下一次或待执行调度记录。
- `schedule_execution`：某个计划触发点的一次执行尝试及结果。

## 3. 全局一致性原则

### 3.1 消息采用逻辑失效，不优先物理删除

消息至少需要区分：

- `ACTIVE`：可进入上下文；
- `INVALIDATED`：因取消、回滚或替代而失效；
- `SUPERSEDED`：被新的 run 或引导分支替代；
- `PARTIAL`：流式生成中，尚未形成可提交结果。

失效动作需要记录 `invalid_reason`、`invalidated_at`、`invalidated_by_run_id`。上下文查询、压缩取数、导出、记忆提取等所有读取路径都必须明确过滤规则，不能只在聊天列表接口里隐藏。

### 3.2 所有异步结果必须基于版本校验后提交

压缩任务启动时记录：

- `base_context_revision`；
- 覆盖的消息边界或明确的消息 ID 集合；
- 覆盖内容的稳定 hash；
- 任务所属 session/run；
- 上一个可恢复快照。

任务完成后只能通过 CAS（比较并交换）激活：当前上下文版本、消息有效性和覆盖 hash 均未变化时才允许成为活动快照。任务“计算完成”与结果“正式生效”必须是两个状态。

### 3.3 工具调用前必须经过统一执行闸门

模型产生工具调用意图后，真正调用外部工具之前必须执行统一检查：

1. run 是否仍处于可执行状态；
2. 是否收到取消或待处理引导；
3. 上下文版本是否仍与当前 run 一致；
4. token 是否超过工具调用前压缩阈值；
5. 压缩是否正在执行，当前策略是否要求等待；
6. 工具调用是否已经以同一幂等键提交过。

该闸门应是所有工具调用的唯一入口，不能依赖每个工具自行实现检查。

### 3.4 取消只能保证“尚未产生的副作用不再产生”

已经完成的外部工具副作用通常无法可靠撤销。产品和接口必须区分：

- 已阻止：工具尚未调用；
- 中止中：工具支持中断，正在请求中断；
- 已执行：外部副作用已经产生，只停止后续步骤；
- 可补偿：存在明确的补偿动作，但补偿不是默认行为。

## 4. 需求一：工具调用前的上下文压缩

### 4.1 当前需求

保留现有“消息发送后、模型检测前”的 token 阈值检查，同时新增“工具真正调用前”的第二检查点。如果超过阈值，应触发压缩，并在压缩结果安全生效后再决定是否调用工具。

### 4.2 推荐流程

1. 模型返回工具调用意图；
2. 进入统一工具执行闸门；
3. 先检查取消和引导；
4. 计算当前有效短期上下文 token；
5. 未超阈值：继续工具调用；
6. 超过阈值：创建或复用同范围的压缩任务，将 run 置为 `WAITING_COMPACTION`；
7. 压缩任务完成后执行版本、有效消息和覆盖 hash 校验；
8. 校验通过则激活快照、推进上下文版本并恢复 run；
9. 恢复后再次检查取消、引导和工具幂等键；
10. 所有条件满足才调用工具。

### 4.3 必须处理的边界

- 同一范围已经有压缩任务时应复用或等待，不能重复压缩；
- token 在压缩后仍超阈值时，需要有最大重试次数和降级策略；
- 等待压缩期间收到取消：停止恢复执行，并废弃相关压缩结果；
- 等待压缩期间收到引导：旧 run 不直接继续，按引导策略重建上下文；
- 压缩失败：明确选择“有限上下文降级”“返回可重试错误”或“停止执行”，不可静默带着超限上下文继续；
- 工具参数已经由模型生成但工具尚未调用时，压缩后是否复用旧参数必须由版本规则决定。推荐上下文有变化就重新推理，不直接复用旧工具意图。

### 4.4 验收标准

- 构造超过阈值的工具调用场景，工具在压缩安全生效前不会执行；
- 压缩等待期间取消，工具调用次数为 0；
- 并发压缩只激活一个与当前版本匹配的结果；
- 旧版本压缩晚到时不会覆盖新上下文；
- 相关状态、等待时长、token 变化和失败原因可观测。

## 5. 需求二：取消正在执行的会话

### 5.1 产品语义

取消对象应是明确的 `run_id`，而不是模糊的 session。前端在生成中将“发送”切换为“取消”；取消请求必须幂等。用户取消后：

- 停止继续生成和后续工具调用；
- 将本 run 尚未提交或不应保留的消息标记失效；
- 已完成且属于此前 turn 的有效历史不受影响；
- 向用户展示最终取消状态，以及是否已有工具副作用发生。

### 5.2 推荐状态机

`CREATED -> RUNNING -> WAITING_TOOL / WAITING_COMPACTION -> COMPLETED`

任一可取消状态可进入：

`CANCEL_REQUESTED -> CANCELLING -> CANCELLED`

如果取消到达时 run 已结束，应返回既有终态，不能把 `COMPLETED` 反向改成 `CANCELLED`。

### 5.3 取消原子操作

取消事务至少完成：

1. 以 run 版本号更新为 `CANCEL_REQUESTED`；
2. 推进 session 的 `context_revision`；
3. 将该 run 的 partial assistant、未执行工具请求、未提交工具结果等标记失效；
4. 标记与失效消息相交的压缩任务为 `CANCEL_REQUESTED` 或 `STALE`；
5. 发布取消信号，使流式生成、模型调用、工具执行器和压缩 worker 尽快感知；
6. 写入审计事件。

数据库状态是最终事实来源；进程内信号或 Redis Pub/Sub 只用于加速感知，不能作为唯一取消依据。

### 5.4 与压缩任务的适配

按压缩状态分别处理：

- 未开始：直接取消；
- 执行中：请求中断；若无法硬中断，允许计算结束但禁止激活；
- 已完成未激活：标记 `STALE`，禁止激活；
- 已激活且覆盖了待取消消息：撤销该快照的活动资格，恢复最近一个不包含失效消息的祖先快照；若无安全祖先，则从有效消息重建上下文；
- 已完成且覆盖范围与取消消息无交集：可以保留，但仍需通过当前 context revision 的兼容性校验。

压缩范围不能只用不稳定的列表下标表达；至少应保存稳定消息边界和内容 hash，推荐保存覆盖消息清单或可追溯快照血缘。

### 5.5 工具调用保护

- 工具执行器领取任务前检查取消；
- 真正发出外部请求前再次检查取消；
- 使用 `run_id + tool_call_id` 作为幂等基础；
- 若取消与外部请求同时发生，记录实际发生顺序和工具结果，不能伪装成“完全未调用”；
- 对支持取消的工具传递 cancellation token；
- 对不支持取消的工具只阻止后续动作，并向前端说明已有副作用。

### 5.6 验收标准

- 重复点击取消不会造成重复状态迁移或异常；
- 取消后不再产生新的模型、工具或压缩消耗；
- 被取消消息不会进入后续上下文、长期记忆、导出内容的默认有效视图；
- 覆盖失效消息的压缩结果不会被激活；
- 取消与完成并发时只有一个合法终态；
- 可从审计日志还原取消发生前后是否已有工具副作用。

## 6. 需求三：引导正在执行的会话

### 6.1 建议定义

“引导”是用户在当前 run 尚未结束时追加方向修正，例如“不要再查网页，先总结已有信息”或“把结果改成表格”。它不是普通的新 turn，也不是简单把文本塞进正在进行的模型请求。

推荐采用“中断旧 run，基于安全检查点重建并恢复”的语义：

1. 用户提交 steer 指令，绑定目标 `run_id`；
2. 服务端持久化 steer 事件并推进 `context_revision`；
3. 当前 run 进入 `STEER_REQUESTED`，停止后续模型/工具动作；
4. partial assistant 和未执行工具意图按策略失效；已完成工具结果可作为事实保留；
5. 处理与旧消息范围相交的压缩任务；
6. 创建 successor run，将 steer 指令作为高优先级用户指令加入有效上下文；
7. successor run 从最近安全检查点继续。

这样可复用取消的大部分安全机制，但最终状态应为 `SUPERSEDED` 而不是 `CANCELLED`。

### 6.2 引导与取消的差异

- 取消：停止且不自动继续；
- 引导：停止旧执行并创建后继执行；
- 取消默认失效当前未完成输出；
- 引导可选择保留已确认事实和已完成工具结果，但不能保留与新指令冲突的未执行工具意图；
- 引导需要记录 `predecessor_run_id` 与 `successor_run_id`，形成执行链。

### 6.3 前端交互

- 生成中同时提供“取消”和“引导”；
- 点击引导后展示小型输入区，不覆盖普通消息输入；
- 提交后展示“正在按新要求调整”；
- 对已产生的工具副作用给出提示；
- 连续引导按服务端序列处理，推荐只让最后一条未处理引导生效，或明确合并规则；禁止无序并行创建多个 successor run。

### 6.4 与压缩的适配

steer 事件必须像消息一样参与上下文版本控制。旧压缩任务若覆盖被替代的 partial 消息则失效；若只覆盖仍有效历史，可复用其祖先快照。successor run 激活任何快照前，仍必须检查 steer 后的上下文版本和覆盖 hash。

### 6.5 验收标准

- 工具调用前收到引导时，旧工具意图不会执行；
- 引导后只存在一条合法的后继执行链；
- steer 指令出现在后继 run 的有效上下文中；
- 已失效 partial 输出不会污染压缩、长期记忆和后续回答；
- 连续引导、引导后取消、取消与引导并发都有确定结果。

## 7. 需求四：会话导出、分享与导入

### 7.1 用户流程

1. 会话所有者点击“分享/转发”；
2. 后端生成版本化会话导出包；
3. 导出包写入 MinIO；
4. 后端返回带有效期的分享链接或分享 token；
5. 接收者访问 Web 特定路由；
6. Web 端请求后端校验分享状态和权限；
7. 后端流式下载或签发短时 MinIO URL；
8. 前端预览导入范围并确认；
9. 后端在接收者名下创建一个新的会话副本。

默认语义是“复制导入”，不是共享同一会话记录，也不转移原始会话所有权。

### 7.2 导出包建议结构

```json
{
  "schemaVersion": "1.0",
  "exportId": "...",
  "sourceSession": { "title": "...", "createdAt": "..." },
  "messages": [],
  "artifacts": [],
  "metadata": {},
  "checksum": "..."
}
```

导出内容应明确：

- 默认只导出有效且已提交的消息；
- partial、cancelled、invalidated、内部系统提示词默认不导出；
- 工具结果、附件、制品是否包含需按类型制定白名单；
- API Key、Cookie、Authorization、用户密钥和内部路径必须脱敏或排除；
- 模型、token 用量、内部 trace 等运维字段默认不对接收者暴露；
- 大附件用对象清单和独立签名引用，不能无限膨胀单个 JSON。

### 7.3 分享记录

建议建立分享记录，至少包含：`share_id`、`owner_user_id`、`source_session_id`、`object_key`、`schema_version`、`checksum`、`status`、`expires_at`、`max_downloads`、`download_count`、`password_hash（可选）`、`created_at`、`revoked_at`。

MinIO bucket 保持私有。优先让分享链接指向后端受控路由，由后端鉴权后流式返回；若使用预签名 URL，其有效期应短于分享本身，且每次访问动态签发。

### 7.4 导入规则

- 校验 schema version、文件大小、checksum 和内容类型；
- 防止 Zip Slip、对象路径穿越和恶意超大包；
- 重新生成 session/message/artifact ID，并维护旧新 ID 映射；
- 导入内容标注来源、导入人和导入时间；
- 不自动继承原会话的私有工具权限、知识库权限、工作流权限或密钥；
- 导入应幂等，重复请求不能产生多个副本；
- 导入失败应回滚数据库记录并清理临时对象。

### 7.5 验收标准

- 链接可过期、可撤销，并支持访问审计；
- 接收者导入后得到独立副本；
- 被取消/失效消息和敏感配置不会默认出现在导出包；
- 旧版本导出包有明确的兼容或拒绝策略；
- 大会话可流式处理，不将整个包一次性加载进内存；
- 越权用户无法下载 MinIO 对象。

## 8. 需求五：分布式定时任务模块

### 8.1 组件定位

可优先评估 XXL-JOB 作为分布式调度和运维控制面，但业务任务的定义、物化、幂等执行和下一次时间推进仍由本项目的数据模型保证。正式选型应在代码与部署环境调研后确认，不在本规划稿中锁死。

系统包含两个分布式作业：

1. **长间隔配置协调器（Reconciler）**：扫描所有启用且配置了 Cron 的业务配置，将其规范化并物化到调度任务表；
2. **短间隔到期任务派发器（Dispatcher）**：扫描已到期任务，分布式抢占执行，记录执行结果并推进下一次执行时间。

### 8.2 长间隔配置协调器

处理步骤：

1. 分页扫描启用的 Cron 配置；
2. 规范化 Cron、时区、任务类型和业务参数；
3. 计算 `config_hash`；
4. 以稳定业务键 `tenant_id + task_type + biz_id` 查找调度定义；
5. 不存在则插入；
6. 已存在且 hash 相同则不更新；
7. 已存在且 hash 不同则冲突更新版本、Cron、参数和下一次执行时间；
8. 对已删除或禁用的来源配置，将调度定义置为禁用，不物理删除执行历史。

这里的“hash 一致性”用于判断配置内容是否变化，不应把 hash 当作唯一业务身份。Cron 改变后仍是同一个任务定义，通过业务唯一键 upsert，禁止产生第二条活动任务。

### 8.3 短间隔到期任务派发器

处理步骤：

1. 查询 `enabled = true AND next_fire_time <= now` 的任务；
2. 使用 `SELECT ... FOR UPDATE SKIP LOCKED`、租约或等价方案抢占；
3. 创建唯一执行记录，唯一键建议为 `schedule_id + scheduled_fire_time + config_version`；
4. 提交事务后执行实际业务逻辑，避免长事务包裹外部调用；
5. 通过心跳延长租约，防止慢任务被误重复领取；
6. 完成后记录结果，并基于本次计划时间计算下一次时间；
7. 使用 fencing token/版本号 CAS 更新，防止旧 worker 覆盖新配置；
8. 失败按策略重试，重试不改变本次计划触发点的幂等身份。

### 8.4 建议表结构

#### `agent_schedule_definition`

- `id`
- `tenant_id`
- `task_type`
- `biz_id`
- `source_config_id`
- `cron_expression`
- `timezone`
- `payload_json`
- `config_hash`
- `config_version`

### 8.5 必须明确的调度策略

- Cron 语法版本与校验规则；
- 时区和夏令时行为；
- Cron 更新后下一次执行时间从“当前时间”还是“上次计划时间”计算，推荐从更新时间后的当前时间重算；
- misfire 策略：跳过、立即补一次、补齐全部，默认建议“立即补一次”；
- concurrency 策略：禁止并发、允许并发、替换旧执行，默认建议同 schedule 禁止并发；
- 最大执行时长、租约和心跳间隔；
- 重试次数、退避和死信处理；
- 配置禁用时对已领取任务的处理；
- 多租户隔离和任务级权限；
- 手动触发是否影响 `next_fire_time`，默认不影响。

### 8.6 前端范围

前端至少提供：

- 调度定义列表、筛选和启停；
- Cron 编辑、校验、时区选择和未来若干次触发时间预览；
- 当前状态、下一次/上一次执行时间；
- 执行历史、耗时、结果、错误和重试次数；
- 手动触发、失败重试；
- 配置 hash/version 和最近同步状态；
- 权限校验、危险操作确认和审计入口。

### 8.7 验收标准

- 多个协调器实例同时扫描不会产生重复活动定义；
- 修改 Cron 后同一业务键只保留一个活动定义，并正确重算 `next_fire_time`；
- 多个派发器同时扫描，同一计划触发点只产生一条逻辑执行；
- worker 宕机后租约可恢复，旧 worker 不能覆盖新 worker 的结果；
- 重试、misfire、禁用、手动触发行为符合已选策略；
- 前端能完整查看定义、下一次执行和执行历史；
- 指标可观测：扫描延迟、到期积压、触发延迟、成功率、重试率、租约超时数。

## 9. 跨模块建议数据能力

代码调研后应判断现有表能否演进；不要仅因字段缺失立刻重建。无论复用还是新建，最终需要支持：

- run 状态、版本号、前驱/后继 run；
- message 有效性、失效原因及所属 run；
- session context revision；
- compaction task 的基准版本、覆盖范围、hash、激活状态和快照血缘；
- cancel/steer 审计事件；
- 分享记录、对象信息、checksum、过期与撤销；
- 调度定义版本、配置 hash、下一触发时间、租约和执行幂等键。

所有新增状态字段应通过显式枚举和合法状态迁移维护，不允许散落魔法数字。

## 11. 核心测试矩阵

| 场景 | 必须保证的结果 |
|---|---|
| 工具前超 token | 压缩安全激活前工具不执行 |
| 压缩中取消 | run 终止，压缩结果不激活，工具不执行 |
| 压缩完成与取消并发 | 通过 context revision/CAS 只得到一个合法结果 |
| 工具请求发出瞬间取消 | 记录真实副作用状态，停止后续步骤 |
| 生成中引导 | 旧 run 被替代，后继 run 使用 steer 后上下文 |
| 连续引导 | 按确定顺序合并或仅最后一条生效，不产生并行分叉 |
| 引导后取消 | successor run 可被准确取消 |
| 分享含失效消息 | 默认导出中不存在失效消息 |
| 分享链接撤销/过期 | 无法继续下载或导入 |
| 重复导入 | 幂等返回同一结果或明确拒绝，不创建重复副本 |
| Cron 修改 | 同业务任务冲突更新，不重复入库，下一次时间正确 |
| 多节点抢占 | 同一计划触发点只逻辑执行一次 |
| worker 宕机 | 租约到期后可恢复，fencing 阻止旧 worker 提交 |

## 12. 待决策项

进入实现前必须明确：

1. “取消当前消息”是否包含已经完整生成但尚未进入下一轮的 assistant 消息；
2. 已成功完成的只读工具结果在取消后是否保留为有效历史；
3. 有外部副作用的工具是否需要逐类提供补偿动作；
4. 引导采用“最后一条覆盖”还是“按顺序合并”；
5. 引导时 partial assistant 是否在 UI 中保留为灰色历史，数据层仍应失效；
6. 压缩失败后的默认降级策略；
7. 分享是否支持匿名访问、密码、最大下载次数和永久链接；
8. 工具结果和附件的默认导出白名单；
9. 导入会话能否直接继续对话，还是需要用户确认模型/工作流配置；
10. 分布式组件最终选 XXL-JOB 还是其他方案；
11. Cron 方言、默认时区、misfire 和并发策略；
12. 定时任务实际业务执行是本地 handler、工作流、Agent run，还是三者均支持。

### 13.3 Phase 3：引导

```text
在已经稳定的 cancel/run/context revision 基础上实现生成中引导（steer）。

- 引导到达后，旧 run 不再发起新的模型或工具调用；

- successor run 必须包含 steer 指令并基于最新有效上下文重建；
- 连续引导采用批准后的确定性合并/覆盖规则；
- 支持引导后取消，并处理引导、取消、完成三者并发；
```

## 14. 完成定义

本阶段只有同时满足以下条件才算完成：

- 功能路径完成，且统一状态模型没有旁路；
- 数据迁移兼容现有数据并可回滚；
- 并发与故障场景有自动化测试；
- 前端能表达真实后端状态，不用假成功掩盖竞态；
- 敏感数据、权限和审计经过检查；
- 核心指标、日志和告警可支持线上定位；
- 文档、接口和部署方式与实际实现一致；
- 灰度期间验证取消后工具调用数、压缩陈旧结果拒绝数、调度重复执行数等关键指标。
